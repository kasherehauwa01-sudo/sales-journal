# Сезонность категорий: первая версия

Отдельный отчёт `/reports/category-seasonality` по подкатегориям второго уровня.
Открытие страницы и редактирование фильтров не читают товарные строки для расчёта.
Расчёт выполняется только кнопкой. Данные и фильтры последнего успешного расчёта
сохраняются в браузерном состоянии; изменение формы отмечается явно. Ошибки не
подменяются пустым отчётом, автоматических повторов нет. Детализация и переключение
штук/выручки используют готовый ответ. Excel, PDF и календарь подготовки не входят
в эту версию. Товарная сезонность из PR184, её API, worker и расписания не возвращены.
«Кандидаты в акцию» и его ранжирование не меняются.

## Источники и иерархия

Изучены текущие CategoryAnalyticsReportPage/category_analytics_report,
CategoryTreeFilter/catalog_category_tree, локальный lookup-контракт и код
CatalogVR (`services/catalog_categories.py`, `schemas/analytics_lookup.py` в
доступном checkout). CatalogVR связывает исходный section с canonical category
через CatalogSectionMapping и сохраняет category_id/category1 у Product. Его
analytics lookup передаёт category_id/category и subcategory (исходный section)
в локальный CatalogProduct. Плоский integration tree не доказывает родителя.

Новый отчёт читает подтверждённые matched CatalogLookup и локальные
CatalogProduct. Родитель подтверждён только при непустых category_id, category и
subcategory. Ключ строки — JSON-пара `["category:<id>", "<subcategory>"]`.
Одноимённые ветки с разными ID не смешиваются. У подкатегории нет отдельного
стабильного ID в текущем контракте, поэтому её переименование меняет ключ.
Без подтверждённого родителя раздел попадает в «Без данных об иерархии»;
несопоставленные продажи — в отдельную строку «Без сопоставления» этой группы.
Legacy_category используется только как подпись неизвестного раздела, не как
доказательство связи. Материал, HoReCa, фотографии и SKU-профили не рассчитываются.

CategoryTreeFilter переиспользован с необязательными providedNodes/kind=id:
поиск, раскрытие, множественный и частичный выбор остаются прежними. Старые
потребители продолжают пользоваться прежними legacy/section значениями и URL.
Выбор родителя разворачивается в множество ключей детей; API также понимает ID
родителя. Проверка членства через OR не дублирует ни mapping, ни продажи.

## Сопоставление и фильтры

PostgreSQL сначала возвращает курсором DISTINCT пары исходных code/article
(не строки продаж). Порциями по 500 вычисляется существующий
catalog_attributes.identity: trim + Python casefold, JSON-пара и SHA256. По hash
читается один подтверждённый lookup; приоритет/неоднозначность уже определены
синхронизацией. Никаких fallback по дублирующемуся артикулу нет. Ведущие нули
сохраняются. PostgreSQL lower() не заменяет Python casefold() для идентичности:
например, Straße и Unicode-пробелы тестируются отдельно.

Небольшая TEMP-проекция исходная пара → ветка заполняется последовательно. Она
содержит только идентификаторы и ветку, не товары/фотографии/продажи, автоматически
удаляется rollback транзакции. Это не постоянная таблица и не миграция.
Затем SQL соединяет пары и агрегирует `quantity` и `quantity*actual_price` до
ветки × года × месяца. Формулы и возвраты совпадают с аналитикой категорий;
отрицательные величины не обрезаются. В Python/браузер поступают только месячные
итоги. Разные исходные пары одного товара не размножают строки продаж.

Магазины фильтруются точно по Sale.department. Менеджер и вид покупателя используют
get_sales_filter_clients и те же ClientsVR-справочники, включая «Нет менеджера»,
нормализацию и пересечение списков. Отказ ClientsVR при выбранном фильтре — 502,
не ложный пустой отчёт. Бренд/производитель — разные точные локальные поля
CatalogProduct; ИЛИ внутри списка и И между фильтрами. Пустые списки не ограничивают.
Проекция и суммы читаются в одной REPEATABLE READ транзакции. Каталог не запрашивается
по сети. Профиль использует текущие локальные характеристики, не исторический срез.

## Покрытие: строгий доступный признак и его ограничения

Исторический контроль файлов в main уже удалён. Старые ImportRule/ImportDayCheck
нельзя считать актуальным утверждённым реестром магазинов. Новый «Контроль продаж»
проверяет наличие продаж и тоже не доказывает полноту месяца.

Покрытие строится независимо от категории, бренда, производителя, менеджера и вида
покупателя. Используются только ImportReceipt со status=success,
period_method=DECLARED_REPORT_PERIOD, успешным ImportBatch, error_rows=0 и
ненулевым file_size. Объявленный период извлекается существующим проверенным
парсером source_period из заголовка реальной выгрузки 1С. OBSERVED_SALES, ошибки,
незавершённые импорты и неподтверждённые периоды не используются.

Для каждого подразделения из receipt.departments объединяются дни объявленных
интервалов. Месяц покрыт только при покрытии каждого календарного дня каждого
магазина области расчёта. При пустом фильтре область — объединение наблюдавшихся
за выбранные годы подразделений продаж и подтверждённых receipt.departments.
При выбранных магазинах проверяются именно они. Новое/закрытое подразделение без
полного года исключает год из общей модели этой выборки; можно выбрать более
узкий магазин. Отсутствие метаданных не исправляется обращением к 1С или повторным
импортом. Успешный нулевой файл без определимого подразделения не подтверждает
покрытие: нельзя угадать магазин. При наличии покрытия отсутствие отфильтрованных
продаж считается подтверждённым нулём.

Это подтверждение успешной обработки **заявленного периода файла**, а не
независимая гарантия, что 1С не пропустила продажи внутри него. Полного актуального
исторического реестра открытия/закрытия магазинов и исторических остатков нет.
Полностью отсутствующее в продажах и метаданных подразделение обнаружить нельзя.
Удаления продаж оператором без изменения метаданных также нельзя диагностировать
через receipts. Эти ограничения явно показаны в отчёте. Если старые импорты имеют
только OBSERVED_SALES, фактические суммы показываются как неполные, а индексы
не рассчитываются. Не заполнять им period_method вручную ради появления индексов.
Для более сильной гарантии нужен отдельно согласованный контракт покрытия.

## Методика

Предлагаются последние три завершённых года, в которых есть продажи; можно
выбрать другие завершённые годы. Текущий/будущий год отклоняется. Покрытие каждого
из 12 месяцев обязательно. Для каждой метрики годовая база = сумма/12; нулевая
или отрицательная база исключает год. Индекс = (месяц/база−1)×100%; отрицательные
месяцы возвратов допустимы. Типичный месяц — медиана годовых индексов пригодных
лет; расчёт ведётся Decimal до выдачи чисел JSON. Данные непригодных лет сохранены
отдельно с причиной. Неподтверждённый месяц не отображается как полный: его
наблюдавшаяся сумма подписана в скобках рядом с «Нет данных».

Пик — максимум медианного профиля ≥ +20%. При равенстве выводятся все месяцы.
Для каждого пика считается число пригодных лет с индексом этого месяца ≥ +20%.
Повторяющийся: минимум 2 таких года и `3*count >= 2*total`. Один год даёт профиль
и фактические суммы, но явную пометку о недостатке данных для повторяемости.
Нет пригодных лет — нет индекса. Сводная строка родителя не рассчитывается:
родитель только заголовок группы. Диаграмма использует единую ось процентов;
фактические штуки/рубли находятся отдельно в таблице.

## Ресурсы и воспроизводимые замеры

ReportRoute + get_report_db переиспользуют общую heavy_operation: блокировка
до чтения тела и до завершения ответа, ограниченная очередь, headroom, корректная
отмена/rollback. Параметры запроса прежние: serial PostgreSQL plan, work_mem=4MB,
hash_mem_multiplier=1, statement_timeout=60s, lock_timeout=2s. Лимиты не повышались.
Чтение идентификаторов и receipts курсорное, покрытие хранится компактными
битовыми масками годов/магазинов. На ответ стоит предел 5000 групп и проверка
headroom. Нового кеша, фонового процесса, индексов, расширений БД или постоянного DDL нет.

Локальный PostgreSQL16 в контейнере с лимитом 256МБ/1 CPU; база только синтетическая,
120000 продаж, 480000 строк, 12000 товаров, 120 веток, 12 магазинов, 2023–2025.
Полный расчёт включает discovery, matching, TEMP, агрегирование, покрытие и профиль,
но не HTTP-сериализацию. EXPLAIN ANALYZE запускается отдельно после измерения.
Результат одного запуска, а не медиана и не обещание производительности FirstVDS:

| Выборка | Время полного расчёта | Строк профиля | RSS Python до → после |
|---|---:|---:|---:|
| Без фильтров | 3478,0 мс | 120 | 87,45 → 90,23 МиБ |
| 2 магазина, 2 бренда, 2 производителя, менеджер + вид покупателя (подставной справочник) | 172,1 мс | 4 | 90,23 → 90,29 МиБ |

Это финальный запуск без параллельного тестового набора. Широкий запрос выполнен первым; второй имеет преимущество прогретого cache. Предыдущий запуск при одновременных тестах занимал 9,76с/0,25с, что иллюстрирует зависимость от загрузки стенда.
Вся история не загружалась в Python. Peak RSS процесса по ru_maxrss около 89,94МиБ;
это измерение процесса теста, не пика всех контейнеров/ОС. RSS PostgreSQL ограничен
его локальным cgroup, но суммарный пик сервера отдельно не измерялся.

План широкого агрегирования: hash join 480000 items с TEMP 12000 пар,
индексные обращения к sales, сортировка/агрегация в 4320 месячных строк;
при 4МБ work_mem сортировка использовала временные блоки (3745 read/3757 write).
Отфильтрованный план: bitmap indexes sales.department/client, 4000 продаж,
16000 item-проб, TEMP 56 пар, 2240 прошедших строк, 144 месячных итога;
без дискового spill. Полные планы и цифры: `benchmarks/category_seasonality.json`.
На многомиллионной базе широкий запрос может упереться в 60с/IO; он завершится
контролируемым 503. Следующий шаг при подтверждении этого риска — отдельно
согласованные помесячные предагрегаты с корректной инвалидацией, не увеличение
таймаутов и не отключение защиты.

Воспроизведение: задать IMPORT_CONTROL_TEST_DATABASE_URL только на localhost,
БД с именем import_control_test (fixture откажет другому адресу/имени), затем:

```bash
PYTHONPATH=backend CATEGORY_SEASON_BENCHMARK=1 .venv/bin/pytest -q \
  backend/tests/test_category_seasonality_postgres.py
```

Fixture создаёт и удаляет собственную случайную схему, не рабочие таблицы.
Без флага большой benchmark пропускается. Не запускать эту команду на VPS.

## Проверки и установка

Покрыты отдельные апрель/июль у одного родителя, одноимённые ветки, неизвестный
родитель, parent+child без дублей, leading zeros/дубли артикула/casefold, все фильтры,
возвраты, разовый пик, ровные/нулевые/отрицательные данные, равные максимумы,
високосный февраль, недостаток покрытия/истории, 502, текущий год, HTTP и изоляция.
Backend regression: 1033 passed, 341 skipped (не настроенные внешние/PostgreSQL fixtures); cross-repository Calltrack contract исключён без соседнего checkout. После этого дополнительный тест порога входит в целевой набор из 11 passed. Изолированный PostgreSQL16: 3 passed, включая явный benchmark и HTTP. Frontend: 171 passed, сборка TypeScript/Vite успешна (существующее предупреждение chunk >500kB).

Frontend проверяет отсутствие автозапроса, выбор фильтров, single-flight,
503/ручной retry, обе метрики и разные детализации. Настоящий локальный Chromium
проверяет клавиатуру/Escape/возврат фокуса, сохранённые фильтры и мобильный scroll.
Скриншоты синтетических данных: `screenshots/category-seasonality/`.

Для установки нужны готовые новые backend/frontend образы, собранные вне VPS;
схема28 не меняется. Использовать штатный безопасный updater. Ничего не включается
по расписанию, первоначального заполнения нет. Откат — предыдущие образы,
без downgrade БД. Production не подключался и не изменялся.
