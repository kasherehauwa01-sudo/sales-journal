# Сезонность категорий: опубликованный недельный снимок (schema29)

Отчёт отвечает на один вопрос: в какие календарные месяцы продажи подкатегории
выше/ниже её собственного обычного уровня. Категория первого уровня только
группирует строки. Товарная сезонность PR184, её API, таблицы и расписания не
возвращаются. «Кандидаты в акцию», его оценки и другие отчёты не меняются.

## Снимок вместо расчёта по кнопке

При открытии страницы выполняется только быстрый запрос опубликованного снимка.
Фильтры обновляют карту автоматически с debounce 200мс; старый ответ не может
перезаписать новый выбор (AbortController + последовательный номер). При ожидании
или ошибке прежний результат явно подписан. Ошибка не становится пустым отчётом,
повтор быстрого запроса ручной. Кнопки запуска тяжёлого расчёта в отчёте нет.

Обе метрики возвращаются вместе; переключатель не делает нового запроса. Карта
содержит только индексы и состав ячеек. Детализация читает помесячные факты одной
подкатегории с переданным snapshot_id и теми же фильтрами. Оба ответа согласованы
в REPEATABLE READ. Старый недоступный снимок вызывает 409, а не подмену новым.
В браузер не выгружается весь многомерный снимок. В сравнении год к году и в
сравнении с соседним месяцем отчёт не участвует. PDF/Excel/календарь не добавлены.

## Иерархия и фильтры

Переиспользованы подтверждённые CatalogLookup/CatalogProduct из lookup API CatalogVR
и CategoryTreeFilter с поиском, раскрытием и частичным выбором. Родитель считается
подтверждённым только при category_id + category + subcategory. Ключ включает ID
родителя и подкатегорию; одноимённые ветки разных родителей не объединяются.
Плоский tree или legacy_category не доказывает родителя: неизвестные связи остаются
в отдельной группе. Parent+child — проверка принадлежности множеству, не JOIN,
дублирования продаж нет.

Коды/артикулы сопоставляются существующим Python identity (trim/casefold,
SHA256 пары). Пары стримятся по 500, ведущие нули сохраняются, неоднозначные lookup
не используются как matched. Никакой замены на приблизительный поиск по артикулу.
Временная проекция нужна только построителю, автоматически удаляется при rollback.

Фильтры: магазин, ветка, бренд, производитель, менеджер, вид покупателя и годы.
Пустой список — вся история/все значения. Разные фильтры пересекаются (И), значения
одного списка объединяются (ИЛИ). Менеджер и вид покупателя фиксируются через те
же get_sales_filter_clients и ClientsVR loaders, что использует аналитика категорий;
пустые/ошибочные ответы не подменяются успешными данными. При первой/еженедельной
публикации замораживаются доступные значения и принадлежности клиентов. Момент
обновления разных API ClientsVR не атомарен на стороне источника: согласованного
source snapshot/version API нет. После публикации фильтры используют только
зафиксированные принадлежности и вообще не обращаются к ClientsVR/CatalogVR.

Для большого прохода ClientsVR не заполняется кешами всех значений: используется
контекстный uncached режим тех же loaders. TTL=300 и кеш других запросов не меняются.
Ответ внешнего API при построении ограничен 8МиБ: превышение завершает новую сборку
ошибкой, оставляя предыдущий снимок. Если существующий fallback ClientsVR слишком
тяжёл для этого лимита, нужен подтверждённый облегчённый API; лимит не повышать
вслепую. Ключи/клиенты/токены в диагностические сообщения не попадают.

## Пригодность месяца (по магазину)

Текущий незавершённый месяц исключается по Europe/Moscow; фиксированных лет нет.
Обрабатывается вся история до первого дня текущего месяца. Начало области магазина
берётся по первым наблюдениям/подтверждённым интервалам, месяцы до появления
магазина не создаются как нулевой спрос. Отсутствие одного месяца не исключает год.

1. `confirmed`: каждый календарный день покрыт успешными ImportReceipt с
   DECLARED_REPORT_PERIOD, корректным подразделением и completed ImportBatch без
   ошибок/с ненулевым файлом. Это подтверждает обработку заявленного периода,
   а не независимую полноту выгрузки 1С.
2. Иначе `estimated`: число разных дат с продажами / календарные дни ≥0,90.
   Единственный порог REGULARITY определён в category_seasonality.py. Считаются
   даты всех продаж магазина независимо от товарных и клиентских фильтров.
   Это регулярность записей, не гарантия полноты данных/наличия товара.
3. Иначе `excluded`: месяц показан в фактических данных как неполный и не входит
   в индекс. 14/30, 18/31, 1/30 не проходят, названия магазинов не влияют.

При confirmed отсутствие подходящих строк — подтверждённый ноль. При estimated
без подходящих строк значение неизвестно, не ноль. При наличии строк и сумме 0
(например, возвраты компенсировали продажи) наблюдавшийся ноль допустим. Полного
исторического реестра наличия/открытия магазинов нет; это ограничение оценок.
Последний включённый месяц — последний confirmed/estimated, а не просто граница
сканирования. Данные непригодных месяцев доступны в детализации с причиной.

## Формула

Для каждой подкатегории и метрики (quantity; quantity*actual_price) сохраняются
возвраты и действующие формулы. Сначала по каждому магазину:

- типичное значение календарного месяца = среднее пригодных наблюдений этого
  месяца всех выбранных лет;
- база = среднее типичных значений представленных календарных месяцев с равными
  весами месяцев (три сентября не весят больше двух январей);
- индекс = (типичное значение / база − 1) × 100%.

При одном календарном месяце или неположительной базе индекс отсутствует.
Если представлены не все 12 месяцев, это указано. Для сети усредняются готовые
**индексы магазинов** с равными весами; сырые обороты сети для нормирования не
складываются. Изменение состава магазинов даёт ориентировочный профиль. Для каждой
ячейки сохранены участвующие магазины, число магазинов, разные годы/их число,
ориентировочность, примечания и причины отсутствия данных. Один год подписан и не
даёт утверждения о повторяемости.

Пик спроса — строго положительный максимум, максимальный спад — строго
отрицательный минимум. Все равные экстремумы отмечены до округления, нет порога
+20%; нули и неизвестные ячейки не отмечаются. Шкала процентов относится только к
собственному обычному уровню, не к другому месяцу/году. Расчёт Decimal, PostgreSQL
NUMERIC без дополнительного округления фактов; JSON содержит числовые значения.

## Хранение (новые таблицы, не старые сезонные агрегаты)

Миграция `20261114_29` после `20261112_28` создаёт пустые таблицы:

- category_season_snapshots: версия, попытка/неделя, статус, граница сканирования,
  замороженные справочники/options, счётчик фактов, время/код ошибки;
- category_season_state: активный ID и ближайший допустимый плановый запуск;
- category_season_categories: подтверждённые подписи/ключи веток снимка;
- category_season_clients: нормализованное имя клиента → внутренний ID снимка;
- category_season_memberships: замороженные client-ID → менеджер/вид покупателя;
- category_season_facts: observed совместное зерно категория × client-ID × магазин
  × бренд × производитель × год × месяц; точные суммы и число строк;
- category_season_coverage: пригодность/дни на уровне магазин × год × месяц.

Не сохраняются все комбинации фильтров: только реально наблюдавшиеся совместные
измерения. Один клиент может иметь несколько принадлежностей; EXISTS исключает
размножение сумм. Клиентские имена нужны для замораживания правил, не выдаются
публичным API и не логируются. Нет фотографий/копий исходных строк продаж.
PK/FK/CHECK/unique и небольшие индексы относятся только к новым таблицам. Состояние
общей ревизии продаж, PostgreSQL настройки, старые данные и индексы не меняются.

Построение происходит в отдельной REPEATABLE READ транзакции. Снимок и активный
указатель публикуются одной фиксацией после всех стадий. Ошибка/отмена откатывает
факты; попытка получает безопасный код ошибки. Предыдущий снимок остаётся доступен.
Сохраняются факты активной и предыдущей публикации; более старые факты удаляются
с запретом нового чтения retired поколения. Большие справочники retired-поколений очищаются; компактные метаданные недельных попыток остаются
для защиты от повторов. Пиковый диск включает прежние две версии + строящуюся
третью + WAL и временные файлы SQL. Размер надо проверить перед первым заполнением.

## Планировщик и ресурсы

Используется existing background_workers.periodic, без нового контейнера/cron.
Плановый момент — суббота 19:00 Europe/Moscow, poll 60с. Сохраняются next_due и
уникальная недельная попытка. Рестарт/несколько backend не создают повторный
автоматический расчёт за уже начатую неделю, даже после ошибки. Пропущенный
запланированный запуск может быть выполнен после рестарта; лавины catch-up нет.

Первого снимка нет → periodic возвращает uninitialized, исходная история не
читается. Первый запуск явно делает оператор командой ниже; после успешного
заполнения следующий расчёт — ближайшая будущая суббота19:00, не немедленно при
рестарте. Ручной повтор возможен осознанно, автоматических повторов ошибки недели
нет. Погибший владелец помечается worker_interrupted после получения lock.

Весь построитель защищён heavy_operation/headroom и прежними lock IDs:
WORKER 734190221 exclusive, SOURCE 734190220 exclusive, CATALOG 734190117 shared.
Активный импорт/каталог/RFM/обновление не обходятся: nonblocking busy откладывает
попытку; перед публикацией владение всеми тремя проверяется. У updater остаётся
его schema lock и прочие guards. SQL serial, work_mem=4MB, hash multiplier1,
statement timeout60s, lock timeout2s — прежние ограничения, не повышались.

Быстрые запросы сериализуются отдельным PostgreSQL transaction lock 734190292 (включая несколько backend): ожидание ≤1с, затем контролируемый503; освобождение при rollback/отмене. Они **не захватывают глобальный тяжёлый слот**, иначе старый снимок
был бы недоступен при обновлении. Они читают только новые таблицы, используют
REPEATABLE READ, serial/work_mem4MB и более короткий statement timeout5s. Ошибка
быстрого запроса никогда не запускает материализацию. Python держит только
агрегаты выбранной области, а не весь многомерный снимок; headroom проверяется
при потоковом чтении и построении строк ответа.

## Изолированные замеры

PostgreSQL16, собственный локальный контейнер с лимитом 256МиБ/1CPU;
120000 продаж / 480000 строк / 12000 товаров, история2023–2025, 12 магазинов.
Справочники ClientsVR подставные; сетевую длительность production они не измеряют.
`docs/benchmarks/category_seasonality_snapshot.json`:

- недельное построение 9,5с;
- 60480 фактов, 552 store-month записей покрытия, 4 принадлежности тестовых клиентов;
- все snapshot-таблицы/индексы одной версии: 11984896 байт (≈11,43МиБ);
- RSS процесса теста до/после: 90,89 → 91,91МиБ, peak ≈91,64МиБ;
- широкая карта120строк: 537мс cold / 459мс warm;
- несколько фильтров одновременно4строки: 38мс cold / 30мс warm.

Cold = перезапуск только изолированного PostgreSQL-контейнера и пустые shared
buffers, но OS filesystem cache не сбрасывался. Warm — повтор на новой сессии.
Замеры чтения включают SQL и формирование индексов Python, не сеть/React/HTTP
сериализацию. Это не измерение FirstVDS и не гарантия той же скорости на 4,6млн
строк. Размер фактов зависит от фактической кардинальности совместных измерений;
в худшем случае приближается к числу исходных позиций. На более крупном наборе
нужны запас для 3 поколений/WAL и повторные стендовые измерения. Лимиты не повышать.

Воспроизведение только localhost БД import_control_test:

```bash
PYTHONPATH=backend CATEGORY_SEASON_BENCHMARK=1 .venv/bin/pytest -q \
  backend/tests/test_category_seasonality_postgres.py
```

Cold-прогон дополнительно требует явной переменной
CATEGORY_SEASON_COLD_RESTART_CONTAINER=sales-control-benchmark-test, проверяет
строго localhost:18539 и это имя. Он не предназначен для VPS/production.
Fixture создаёт/удаляет только свою случайную схему. Никаких реальных писем/API.

## Установка и откат

См. `category_seasonality_deployment.md`. Миграция явная, без заполнения, текущий
production updater28 не объявляется совместимым с29. Пересобираются оба образа
вне VPS, production автоматически не меняется. Старые агрегаты товарной сезонности
не используются. Откат не удаляет таблицы и не выполняет Alembic downgrade/stamp.
