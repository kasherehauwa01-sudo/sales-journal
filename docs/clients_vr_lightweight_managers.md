# Облегчённая интеграция менеджеров Clients VR

## Проверенный контракт

Clients VR PR #77: https://github.com/kasherehauwa01-sudo/clients_vr/pull/77
Изучены main `f74a90b`, `backend/app/api/sales_journal.py`
(client_managers_query, load_client_managers, integration_client_managers)
и `backend/tests/test_client_managers_api.py`.

GET /api/integration/client-managers, Bearer Integration token, JSON dict[str,str].
Имя нормализуется через split/join/casefold, менеджер — strip. Пропускаются
архивные записи, пустые имена и пустые менеджеры. Последний непустой менеджер
побеждает в прежнем порядке lower(trim(name)), id. Пустой словарь допустим.
На стороне Sales Journal сохранена нормализация и тип dict[str,str],
проверяется весь ответ до кеширования. Некорректная структура вызывает ошибку,
а не частичное сопоставление. URL настройки уже включает /api; к нему
добавляется только /integration/client-managers.

## Изменения

get_client_managers использует только новый маршрут: нет резервной полной
загрузки, публичного обхода авторизации или автоматических повторов.
Существующие Bearer-заголовок, timeout 15 секунд и TTL 300 секунд сохранены.
HTTP-ошибки, таймаут и некорректный ответ преобразуются в ClientsVrError с
безопасным сообщением без URL, токена или содержимого запроса/ответа.
Просроченный кеш не выдаётся за успешный ответ; ошибка не заменяет кеш.

get_client_metadata сохраняет прежний результат RFM и кеш видов покупателей,
но больше не записывает в client-managers. Его полный payload остаётся
в отдельном client-metadata-source; потребители менеджеров используют только
новый маршрут. Возможен разный возраст данных RFM и аналитики менеджеров
в пределах существующего TTL, как и раньше при независимых загрузках.

product_reports.managers теперь возвращает HTTP 502 при недоступном
сопоставлении вместо назначения всех продаж группе «Нет менеджера».
Реальное отсутствие менеджера при успешном ответе продолжает обрабатываться
как прежде. Формат успешных отчётов, сравнение периодов, фильтрация одного/
нескольких менеджеров, детализация и экспорт не меняются.

## Аудит оставшихся запросов

| Функция | Потребители | Остаточный риск |
|---|---|---|
| get_client_managers/get_client_manager | product_analytics: фильтры, manager-options, детали; analytics.managers; product_reports: менеджеры, детали, экспорт | Новый компактный маршрут. Полная карта всё ещё занимает память; кеш процесса, нет single-flight в существующем _cached |
| get_client_metadata | rfm_report._dataset | Полный /integration/clients, кеш полного payload и проекций на 300 секунд; RFM по-прежнему может создавать нагрузку |
| get_client_buyer_types | Прямых вызовов в app не найдено | Полный /integration/clients, не изменён для совместимости |
| get_buyer_types | integrations.buyer_types | Основной /integration/buyer-types лёгкий; fallback /integration/clients и /clients остаётся тяжёлым |
| get_managers | integrations.managers; product_analytics.manager_options | Основной /integration/managers лёгкий; поздние fallback могут загрузить полный справочник |
| get_manager_clients | RFM, scenarios, sales_client_filters, product_reports, integrations | Обычно /integration/clients?manager=...; тяжёлый fallback полного справочника при ошибках совместимости |
| get_buyer_type_clients | RFM, product_reports, sales_client_filters, analytics | Сначала существующий /integration/buyer-types/{type}/client-names; полного нефильтрованного fallback нет |

Источники: backend/app/services/clients_vr.py; перечисленные routers и services.
Старые fallback не вызываются из get_client_managers. Они требуют отдельного
обсуждения совместимости и тестов, не заменены неподтверждёнными маршрутами.
Общие ошибки остальных клиентов пока используют прежний обработчик _cached.

Для устранения полной загрузки RFM нужен отдельно согласованный компактный
API клиент→вид покупателя (те же нормализация, порядок дублей, правила пустых
значений и архива) либо согласованная проекция client→{manager,buyer_type}.
Важно определить полноту, детерминированные дубли и поведение при ошибках;
не вводить пагинацию без согласованного снимка/полноты. Затем RFM можно
перевести на лёгкие проекции без кеша полного payload. Такие маршруты сейчас
не предполагаются и не добавляются этим PR.

## Проверки и развёртывание

Тесты используют только подменённую сеть и изолированные данные. Проверены
сравнение со старым алгоритмом, дубли, отсутствие менеджера, несколько
менеджеров, Bearer/timeout, точная граница TTL, ошибки/некорректный JSON,
отсутствие тяжёлого fallback, изоляция кеша RFM и HTTP 502 отчёта.

1. Сначала обновить Clients VR до версии с PR #77 штатным согласованным процессом.
2. В тестовом окружении проверить новый маршрут с действующим Bearer-токеном;
   не записывать токен или полную карту в логи. Production-нагрузка не нужна.
3. Слить PR Sales Journal, обновить его backend штатным процессом.
   Миграций, изменений PostgreSQL, Docker, swap или переменных окружения не нужно.
   Frontend не изменён. Необновлённый Clients VR даст понятную ошибку HTTP 502.
4. Проверить обычные отчёты, выбор нескольких менеджеров и «Нет менеджера»,
   детализацию и RFM; контролировать ошибки и память без нагрузочного теста.
5. Учесть существующий кеш отчётов: уже сформированные результаты могут
   сохраняться до штатного истечения TTL. Лимиты и TTL этим изменением не меняются.

Откат Sales Journal — вернуть коммит штатным обновлением backend. Данные БД
не изменяются; Clients VR с новым маршрутом совместим со старым клиентом.
Однако откат снова включает тяжёлую загрузку менеджеров и старую обработку
ошибки, поэтому при OOM предпочтительнее временно не запускать эти отчёты.
Автоматическое слияние, деплой и production-запросы не выполнялись.
