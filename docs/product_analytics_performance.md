# Производительность «Товарной аналитики»

## Что было узким местом

До оптимизации браузер одновременно вызывал `summary` и активную вкладку. Оба запроса независимо
группировали `sales`/`sale_items` за основной и сравнительный периоды, а затем повторяли batch-info
CatalogVR. При переключении вкладки весь цикл запускался ещё раз. На объёме около 4,6 млн строк
товаров это давало два одинаковых тяжёлых расчёта уже при открытии страницы.

Теперь frontend использует единый `POST /api/reports/product-analytics/report`. Backend также сохраняет
совместимость старых endpoints, но их одинаковые расчёты используют общий bounded TTL-кеш. В логах
`product_analytics stages_ms` видны времена SQL основного периода, SQL сравнения, CatalogVR и обработки.
Значения фильтров, клиенты, токены и другие секреты в эти записи не попадают.

## Кеш и инвалидация

* TTL — 120 секунд, максимум две записи.
* Максимум одной записи — 32 MiB, суммарно — 48 MiB. Слишком большой результат не кешируется.
* Одновременные запросы с одинаковыми параметрами объединяются single-flight блокировкой.
* Ключ включает все фильтры и `max(sales.id)`, поэтому новый импорт инвалидирует результат даже между
  несколькими worker-процессами. После фонового импорта локальный кеш дополнительно очищается сразу.
* CatalogVR сохраняет собственный кеш метаданных и получает товары пакетами по 250 позиций.

## Индексы и безопасный план production

Уже используются индексы `sales.sale_date`, `sale_items.sale_id`, обычные индексы артикула/кода/имени
и созданный на production `ix_sale_items_code_normalized`. Автоматически создавать дополнительные
индексы при старте приложения нельзя.

Перед добавлением индексов выполните `EXPLAIN (ANALYZE, BUFFERS)` для типичных периодов и фильтров.
Если планы подтверждают последовательные сканирования, отдельно рассмотрите:

```sql
CREATE INDEX CONCURRENTLY ix_sales_date_department
    ON sales (sale_date, department);
CREATE INDEX CONCURRENTLY ix_sale_items_article_normalized
    ON sale_items (lower(trim(article)));
```

Для поиска `ILIKE '%строка%'` B-tree не помогает. Только после проверки расширения `pg_trgm`, свободного
места и нагрузки можно отдельно создать GIN trigram-индексы на `sale_items.name` и при необходимости
`article`. Делать это следует по одному индексу через `CREATE INDEX CONCURRENTLY`, наблюдая за RAM,
временем и размером индекса. В данный PR миграция индексов намеренно не включена.

## Развёртывание

1. Снять резервную копию и сохранить текущие планы `EXPLAIN` для контрольных запросов.
2. Обновить backend и frontend обычной процедурой проекта, без ручного изменения данных.
3. Пересоздать контейнеры приложения; миграций БД в этом изменении нет.
4. Проверить один и тот же отчёт дважды: второй запрос должен иметь `cache_hit=True`.
5. После тестового импорта убедиться, что следующий отчёт пересчитан с новым `max(sales.id)`.
6. Сравнить KPI и уникальные чеки с контрольной SQL-выборкой и наблюдать память процесса.
