# Управляемая фоновая синхронизация VRCatalog

Расширяет `docs/local_catalog_attributes.md` / PR #121. Это инструкция для
оператора после отдельного согласования развёртывания; команды здесь не запускали
на VPS. Production и внешние API не используются в тестах.

## Архитектура и сохранение прогресса

- Существующие `catalog_products`, `catalog_lookups`, `catalog_sync_state` и
  миграция `20261010_15` сохраняются. Новая `20261010_16` создаёт только маленькую
  таблицу `catalog_sync_control` с одной записью управления. Она **не обновляет**
  старые таблицы и не сбрасывает `cycle`, `cursor`, `upper_id`, счётчики или данные.
- `python -m app.catalog_worker` — отдельный экономный процесс. В FastAPI нет
  длительного `BackgroundTasks`, task или каталожного scheduler. FTP и сценарии
  остаются без изменений. Нет нового брокера, Redis или Celery.
- Compose-сервис `catalog-sync` имеет профиль `catalog-sync` и `restart: "no"`.
  Обычный `docker compose up -d` без профиля его не включает. Не добавляйте профиль
  в `COMPOSE_PROFILES`, скрипт общего обновления или автоматический запуск сервера.
- Даже явный запуск/перезапуск worker только делает его доступным для команд:
  старая команда исполнения отменяется, прогресс остаётся. Нужно отдельное
  «Запустить / Продолжить» в веб-интерфейсе. Это намеренная защита от неожиданной
  нагрузки после деплоя/перезапуска; автоматического возобновления нет.
- Отдельный session advisory lock `734190118` допускает один worker. Он не
  мешает ручному CLI, пока worker простаивает. Существующий lock `734190117`
  удерживается на весь активный запуск и исключает CLI/второй расчёт каталога.
  Locks неблокирующие, их соединения не остаются в idle transaction.
- Heartbeat каждые 5 секунд; через 20 секунд статус считается недоступным.
  Worker проверяет владение lock в `pg_locks`, включая проверку после HTTP перед
  записью характеристик. Потеря соединения/lock останавливает запись. Проба API
  запуска использует transaction advisory lock: не оставляет session lock в пуле.
- Запуск сериализуется `SELECT ... FOR UPDATE` одной управляющей записи. Повтор
  возвращает HTTP 409. Web API записывает команду и сразу возвращает HTTP 202;
  работа идёт независимо от браузера. Закрытие вкладки не отменяет принятую команду.
- Остановка записывается в PostgreSQL. Worker завершает текущий пакет, сохраняет
  характеристики и курсор одной транзакцией, проверяет команду перед следующим
  пакетом и отпускает lock. Пауза/ожидание ошибки прерываются командой остановки.
- SIGINT/SIGTERM также останавливают после пакета. При принудительном завершении
  незакоммиченный пакет будет повторён; последний сохранённый курсор не теряется.
  Управляющие счётчики текущего запуска могут недосчитать последний пакет после
  аварии между двумя commit. Каталожные данные, checkpoint и накопительные
  счётчики `catalog_sync_state` атомарны; это источник истины.

## Управление и доступ

В защищённом разделе **Настройки** есть блок «Синхронизация каталога VRCatalog»:

1. **Запустить / Продолжить** — продолжает незавершённый проход с текущего курсора.
2. **Приостановить** — ждёт завершения текущего пакета.
3. **Обновить статус** — лёгкий запрос текущих записей состояния. Автоматического
   запуска, автоматического HTTP-повтора команды или тяжёлого подсчёта строк нет.

Все три API требуют существующую подписанную администраторскую сессию раздела
настроек (`require_settings_admin`). Отдельной системы ролей в проекте нет:
используется существующее право администрировать настройки. POST проверяет
Origin, если браузер его передал. Токены и содержимое lookup не попадают в ответ
или журналы. Worker не предоставляет сетевой порт или публичный API.

- `GET /api/settings/catalog-sync/status`
- `POST /api/settings/catalog-sync/start`, JSON `{"mode":"discovery"}` либо
  `{"mode":"refresh"}`
- `POST /api/settings/catalog-sync/pause`

Статус включает курсор, верхний ID, накопительные результаты сопоставления,
технические ошибки, даты успеха/полного прохода и фактическую среднюю скорость
чтения строк текущего запуска (с учётом HTTP и пауз). Верхний ID **не является**
числом строк или товаров. Процент и ETA отсутствуют: разрывы ID не позволяют
достоверно получить их без дополнительного подсчёта. Счётчики идентификаторов
включают повторные сверки и не являются количеством уникальных товаров.

Для существовавшего до этого PR цикла достоверное время начала неизвестно:
PR #121 перезаписывал `started_at` при каждом CLI-запуске. Интерфейс показывает
«Нет данных», а не принимает время последней попытки за начало цикла. Для первого
цикла, действительно начатого новым worker, время хранится отдельно с номером
цикла. Изменение `started_at` исправлено: продолжение теперь его не перезаписывает.

## Режимы после первоначального прохода

### Продолжить проход / обработать новые продажи (`discovery`)

Незавершённый цикл продолжается **без изменения** его `cycle`, `cursor`, `upper_id`.
При завершении текущей границы worker прекращает исполнение, не начинает следующий
проход. При следующей явной команде читает `MAX(sale_items.id)` через PK; если есть
новые позиции, обрабатывает только диапазон выше прежнего `upper_id` до новой
фиксированной границы. `cycle` сохраняется: уже проверенные пары код/артикул не
запрашиваются снова, даже если встретились в новых продажах. Если новых ID нет,
команда завершается без lookup. Продажи, добавленные во время запуска за границей,
попадут в следующую явно запущенную обработку новых продаж.

Это инкрементальное **обнаружение новых продаж**, а не обнаружение изменений
характеристик в VRCatalog. Неизменённый импорт не даёт change feed; исправления
код/артикул уже существовавшей позиции с меньшим ID таким способом не обнаружить.
Для переимпорта задним числом нужен отдельный ручной полный CLI-проход.

### Сверить характеристики известных товаров (`refresh`)

Доступно после завершения первоначального прохода. Последовательно читает только
`catalog_lookups` небольшими PK-пакетами, без повторного чтения всей истории.
`refresh_cursor` и фиксированная `refresh_upper` сохраняются отдельно; пауза и
перезапуск не сбрасывают их. Продажи/их курсор не меняются.

Обновляются текущие характеристики, включая NULL/пустые значения. Не найденные и
неоднозначные пары проверяются один раз за явно запущенную сверку, а не бесконечно.
Завершённая сверка останавливается; повтор возможен только по новой команде.
`invalid` для неизменяемых некорректных идентификаторов не отправляется в API.
При неуспехе HTTP остаются прежние данные и checkpoint. При `not_found`/`ambiguous`
последние успешные атрибуты сохраняются для диагностики, но статус запрещает их
использовать в аналитике. Никакого произвольного выбора дубля или ручной подмены.

Сверка сохраняет правила PR #121: нормализованная пара идентификаторов, ведущие нули,
код прежде артикула, без fuzzy matching; категории `category`, `subcategory`,
`legacy_category` раздельны, HoReCa берётся из контракта lookup. Используется пара
код/артикул, как при первоначальной синхронизации; сохранённый product_id не
подменяет идентификаторы исторической продажи. API-клиент по-прежнему поддерживает
приоритет product_id для явного входного запроса с этим полем.

`updated_at` API не отражает все изменения категорий и удаления; надёжного delta/
tombstone API в доступном контракте нет. Поэтому refresh — явная полная сверка
**известных идентификаторов**, а не имитация incremental update. В будущем можно
отдельно согласовать редкую плановую полную сверку известных пар; её автоматический
запуск сейчас не реализован. Новые lookup, созданные другим процессом после границы
сверки, могут попасть только в следующую сверку. На время run CLI исключён lock.
После изменений увеличивается общая revision кеша отчётов, как в PR #121.

## Лимиты и поведение при нехватке ресурсов

| Переменная | По умолчанию | Ограничение / смысл |
|---|---:|---|
| `CATALOG_SYNC_BATCH_SIZE` | 100 | 1–250 **строк продаж** / известных пар за пакет; HTTP не более этого числа |
| `CATALOG_SYNC_PAUSE_SECONDS` | 1 | 0,1–3600 с между пакетами, включая пакеты без HTTP |
| `CATALOG_SYNC_POLL_SECONDS` | 1 | 0,1–10 с проверки команд в паузе/простое |
| `CATALOG_SYNC_RETRY_LIMIT` | 3 | 0–10 дополнительных попыток одного пакета после исчерпания клиентских retry |
| `CATALOG_SYNC_RETRY_SECONDS` | 30 | 1–3600 с, exponential backoff с потолком 3600 с |
| `CATALOG_SYNC_MIN_AVAILABLE_MB` | 256 | Минимум 256 МБ RAM; повышать можно, снижать защиту нельзя |
| `CATALOG_SYNC_DB_TIMEOUT_SECONDS` | 10 | 1–60 с подключения/SQL только worker-соединений |
| `CATALOG_SYNC_DB_LOCK_TIMEOUT_SECONDS` | 2 | 0,1–10 с ожидания SQL lock только worker-соединений |
| `CATALOG_LOOKUP_TIMEOUT_SECONDS` | 15 | 1–60 с одной HTTP-попытки |
| `CATALOG_LOOKUP_MAX_ATTEMPTS` | 3 | 1–3 ограниченных клиентских попытки; без повышения прежнего лимита |

Один последовательный HTTP lookup. Лимит ответа остаётся 8 МБ. У worker пул
максимум 4 PostgreSQL-соединения без overflow: leader lock, run lock, пакет,
heartbeat. Их таймауты не изменяют серверные настройки PostgreSQL или отчёты.
Нет загрузки всей истории в память, `COUNT(*)` по продажам, таблиц временного
полного справочника, table lock, новых SQL-индексов на миллионы строк или кеша
всего каталога. Используются уже существующие PK-индексы.

Перед пакетом читаются дешёвые Linux RAM/cgroup показатели, без использования swap
как доступной RAM. При недостатке памяти — ограниченные ожидания с backoff, затем
пауза до ручной команды. Если RAM-метрики недоступны — остановка с ошибкой, а не
отключение защиты. После API-ошибки курсор не продвигается; HTTP 401/403/ошибки
контракта не повторяются worker, временные ошибки повторяются ограниченно. При
default возможно максимум 4 worker-попытки × до 3 HTTP-попыток = 12 HTTP-вызовов
для проблемного пакета, с задержками. Затем нужна ручная команда.

## Безопасное развёртывание (только оператором)

1. Согласовать окно работ. Проверить текущую версию/резервную копию и безопасно
   остановить ручной CLI и, если уже включён, worker после пакета. Сохранить вывод `python -m app.catalog_sync
   status` для сравнения; ничего не обнулять. Проверить, что профиль worker нигде
   не включён по умолчанию. Не применять `docker compose down -v`.
2. На staging проверить миграцию и команды с несколькими синтетическими строками.
   Проверить доступ админа, команды start/pause, rollback, отсутствие API-вызова
   до явного старта. На VPS не запускать тесты или первоначальное заполнение.
3. Подготовить новые backend/frontend образы по обычной процедуре проекта.
   Существующий Dockerfile backend выполняет `alembic upgrade head` при запуске;
   поэтому пересоздание backend уже является применением миграции и требует
   отдельного согласования. Worker CMD сам миграции не запускает.
4. После согласования применить **только аддитивную** миграцию:
   `docker compose run --rm --no-deps backend alembic upgrade 20261010_16`.
   Она создаёт одну новую таблицу и одну строку; история продаж/каталог не меняются.
   Сравнить старое состояние `cycle/cursor/upper_id` и счётчики. Повторное применение
   штатного Alembic ничего не сбрасывает.
5. Пересоздать backend/frontend обычным способом **без профиля catalog-sync**.
   Проверить health, отчёты, защищённый новый статус. Синхронизация не запускается.
6. Только после отдельного решения включить **простаивающий** worker:
   `docker compose --profile catalog-sync up -d --no-deps --build catalog-sync`.
   Он не обрабатывает ни одной строки до команды администратора. Проверить RAM,
   отсутствие нового `batch` в логах и статус «Приостановлено».
7. Отдельно согласовать длительный проход, затем нажать «Запустить / Продолжить».
   Начать с 100 строк/1 с, следить за RSS/RAM, swap, PostgreSQL и задержками отчётов.
   При деградации остановить и увеличить паузу/уменьшить пакет перед продолжением.

Просмотр только worker-логов: `docker compose --profile catalog-sync logs --tail=100
catalog-sync`. Не публиковать `.env`, конфигурацию с раскрытыми переменными или токены.

## Откат и совместимость CLI

- Сначала «Приостановить», обновить статус и дождаться сохранения пакета. Затем
  `docker compose --profile catalog-sync stop catalog-sync`. SIGTERM использует
  `stop_grace_period: 180s`; не применять принудительный kill для обычной остановки.
- Вернуть предыдущие backend/frontend образы. Новую маленькую управляющую таблицу
  можно оставить: старый код её не использует. Это предпочтительный откат.
- Если отдельно согласован downgrade, **только** `alembic downgrade 20261010_15`
  при остановленном worker; удалится лишь управление. Никогда не откатывать ниже
  `20261010_15`: это удалит локальный каталог. Каталожные данные/курсор не удалять.
- CLI `python -m app.catalog_sync run --max-products 5000 --max-scan-rows 30000
  --batch-size 100` и `status` работают как раньше. После полного завершения старый
  CLI `run` намеренно начинает новую полную сверку, как PR #121. У фонового
  discovery другой безопасный режим — новые ID, без автоматического сброса цикла.
  Пока активен worker-run, CLI получает existing `catalog_sync_already_running`.
  Просто включённый, но простаивающий worker ручной CLI не блокирует.

## Проверки и ограничения

Изолированные автоматические тесты используют маленькие SQLite-наборы, mocked
HTTP и временные PostgreSQL-схемы. Для шести PostgreSQL-тестов задаётся только
`CATALOG_SYNC_TEST_DATABASE_URL=postgresql+asyncpg://…@127.0.0.1:55432/catalog_sync_test`.
Тесты отказываются работать с другим hostname или именем БД; без переменной
PostgreSQL-тесты пропускаются. Production DATABASE_URL они не используют.

Проверяются continuation, stop-after-batch, повторное продолжение, перезапуск без
автозапуска, API/backoff/лимиты, давление RAM, отмена, refresh/NULL/ambiguity,
сохранение checkpoint при потере lock, три конкурирующих start, CLI-lock,
единственный worker, аддитивная миграция и admin/Origin. Существующие тесты
аналитики проверяют точность отчётов и кеш-инвалидацию. Frontend проверяет отсутствие
автостарта, StrictMode, повторный клик, остановку, ручной статус, 503/ручной повтор.

Результаты проверки этой ветки: backend **346 passed, 3 failed**; все 27 новых
backend-проверок прошли, включая 6 PostgreSQL. Три сбоя в `test_vrcatalog.py`
(`test_catalog_tree_and_confirmed_brand_endpoint`,
`test_catalog_directories_are_cached_and_reused`,
`test_catalog_directory_uses_stale_value_on_timeout`) воспроизведены на
неизменённой версии PR #121: **27 passed, 3 failed** при отдельном прогоне этого
файла. Старые тесты ожидают dict дерева, действующая функция требует list;
исправление этого прежнего несоответствия сюда не включено.
Frontend **51 passed**, TypeScript/Vite build прошёл. `docker compose config
--services` подтвердил отсутствие worker в обычном профиле; с явно указанным
профилем он присутствует. CLI `--help` сохраняет `run/status` и прежние параметры.

Импорт модулей worker в отдельном Python-процессе без БД/HTTP дал peak RSS
**50 720 КиБ (около 49,5 МиБ)** в тестовом окружении. Это только стоимость загрузки
модулей, **не** пик работающего worker и не production-измерение. Не следует
считать эту цифру гарантией достаточности RAM VPS.

Риски для VPS остаются:

- Сам отдельный Python-процесс и до 4 DB-соединений расходуют RAM. Отключённый
  профиль не расходует её. Нет доказательства отсутствия OOM на production:
  free-RAM проверки не резервируют память и другие контейнеры могут занять её позже.
- По миллионам строк первый проход всё равно занимает часы. Маленькие пакеты и
  пауза ограничивают интенсивность, а не сокращают число необходимых SQL-чтений.
- Оngoing отчёты имеют свою прежнюю защиту; worker не удерживает analytics lock,
  поэтому RAM других процессов нужно контролировать. Лимиты кеша не повышались.
- Цикл/snapshot фиксирует диапазон Sales Journal, но VRCatalog не предоставляет
  общий snapshot: характеристики разных пакетов могут меняться во время прохода.
- Нет надёжного change feed/tombstones. `not_found` — не доказательство удаления,
  а отдельная явная сверка остаётся необходимой для актуальности старых товаров.
- Долгая HTTP-попытка задерживает корректную паузу; браузер не должен изображать
  мгновенную остановку. Не увеличивать таймауты для ускорения.
