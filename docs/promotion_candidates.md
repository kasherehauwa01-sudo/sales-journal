# Отчёт «Кандидаты в акцию»

Отчёт доступен по адресу `/reports/promotion-candidates` и использует API:

* `POST /api/reports/promotion-candidates` — кандидаты и KPI;
* `POST /api/reports/promotion-candidates/history` — состояние доступности истории;
* `POST /api/reports/promotion-candidates/export` — XLSX с двумя листами.

## Источники

Продажи агрегируются PostgreSQL по `Sale` и `SaleItem`. CatalogVR вызывается пакетами до 5000 товаров через существующий `batch-info`, поскольку для отчёта одновременно нужны свойства, цены и остатки. Название товара не используется для связи с CatalogVR: сначала применяется код, затем артикул. Продажа не исключается, если CatalogVR недоступен или товар не найден.

## Ограничение истории акций

В текущей схеме `SaleItem` отсутствует историческое поле «Вид товара». CatalogVR возвращает текущее свойство товара, но по нему нельзя достоверно восстановить, в какие прошлые даты товар имел значение «Акция месяца». Поэтому вкладка истории явно сообщает, что данные недоступны, а отчёт не придумывает периоды и эффект акции.

Минимальное корректное расширение источника данных: добавить «Вид товара» в каждую позицию исходной выгрузки, хранить его в `SaleItem` на момент продажи и выполнить обычную Alembic migration для нового nullable-поля. После накопления или безопасного backfill исторических значений можно рассчитывать сопоставимые интервалы до, во время и после акции.

## Ограничение остатков CatalogVR

Специализированного lightweight batch endpoint остатков в текущем контракте нет. Рекомендуемое минимальное расширение CatalogVR:

```http
POST /integration/products/stock-map
```

с входом `{"products":[{"code":"...","article":"..."}]}` и ответом с `code`, `article`, суммарным остатком и, при наличии, розничной ценой. После появления такого endpoint отчёт можно перевести с тяжёлого `batch-info`, не создавая N+1.
