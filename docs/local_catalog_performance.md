# Оптимизация чтения локального каталога

Изменение `local_catalog()` относительно main `0a4330a`: временное запоминание
результата каждого identity внутри одного вызова (включая отсутствующие записи),
пакет 1000 вместо 250, выборка 13 необходимых столбцов вместо 23 столбцов двух
ORM-моделей, один SHA-256 на входную строку вместо двух. Ключ временного
словаря — бинарный digest; SQL использует прежнее hex-представление. Полные
характеристики не копируются во второй кеш; разные ключи отчёта получают
независимые словари. Временный словарь освобождается после вызова.

Сохранены исходный порядок, правила конфликтов, статусы, None, фотографии,
категория/подкатегория/legacy_category и снимок REPEATABLE READ вызывающего
кода. Проверка ensure_headroom выполняется перед каждым входным пакетом,
даже если все его идентификаторы уже разрешены. Нет внешних API-вызовов,
изменений схемы, миграций, TTL или лимитов кеша.

Лог содержит только количество входных строк, уникальных разрешённых
идентификаторов, выполненных попыток SQL и время в миллисекундах. При ошибке
счётчики отражают обработанную часть; идентификаторы и значения не логируются.

## Сравнительные замеры

Только синтетические данные в отдельном локальном PostgreSQL 16, Python 3.12,
SQLAlchemy 2.0.36. Контейнер PostgreSQL ограничен 256 МиБ RAM, без swap,
одним CPU, shared_buffers=16MB. Каждый замер — свежий Python-процесс;
время — медиана трёх запусков без tracemalloc, память Python — отдельный
запуск с tracemalloc, RSS — максимальный абсолютный пик процесса из трёх
запусков без трассировки. Подготовка данных не включена в замеры клиента.
База прогрета. Сравнивается только этап local_catalog, не весь отчёт.

36 706 уникальных identity; два полностью перекрывающихся периода дают
73 412 входных строк. Одна намеренная коллизия ключей отчёта. Есть фотографии,
пустые характеристики, ведущие нули, повторные артикулы, все статусы и
отсутствующие lookup. Контрольные суммы всех результатов совпали.

| Данные | Реализация | SQL | Медиана, мс | Пик RSS, МиБ | Пик Python, МиБ |
|---|---|---:|---:|---:|---:|
| Два периода | До, 250 | 294 | 6285.849 | 99.633 | 39.093 |
| Два периода | После, 500 | 74 | 2755.970 | 106.066 | 43.654 |
| Два периода | После, 1000 | 37 | 1083.587 | 107.633 | 44.658 |
| Один период | До, 250 | 147 | 2727.074 | 99.227 | 38.685 |
| Один период | После, 500 | 74 | 2465.878 | 105.387 | 43.574 |
| Один период | После, 1000 | 37 | 934.099 | 106.500 | 44.220 |

Выбран пакет 1000: в этих условиях он заметно быстрее 500 при дополнительных
примерно 1–1,6 МиБ RSS. Относительно исходного варианта RSS вырос на 8 МиБ
для двух периодов и примерно 7,3 МиБ для одного. Это цена временного
запоминания, а не снижение общего пика памяти. Пик Python вырос примерно
на 5,6 МиБ. Подробные исходные замеры: `benchmarks/local_catalog_results.json`.

## Воспроизведение

Не выполнять на production. Использовать отдельную локальную БД
`catalog_perf_test` на localhost; скрипт проверяет имя БД и адрес и не читает
DATABASE_URL приложения. Создаёт и удаляет только свою случайную схему.

```bash
export LOCAL_CATALOG_BENCH_DATABASE_URL='postgresql+asyncpg://postgres:test-only@127.0.0.1:55433/catalog_perf_test'
PYTHONPATH=backend python backend/benchmarks/benchmark_local_catalog.py --run
PYTHONPATH=backend python backend/benchmarks/benchmark_local_catalog.py --run --periods 1
PYTHONPATH=backend pytest -q
```

Без отдельной переменной тест PostgreSQL-снимка пропускается, остальные
регрессионные тесты используют изолированную SQLite. Тест снимка обновляет
шесть синтетических товаров отдельной транзакцией между пакетами: текущий
вызов видит старые значения, следующий — новые. Также проверены границы
пакетов, повторения между пакетами, пропущенные записи, конфликты, точное
равенство исходной реализации, независимость словарей, очистка memo между
вызовами, memory_headroom и безопасная диагностика.

## Ограничения и внедрение

Синтетические результаты не гарантируют такую же скорость на VPS: влияют
swap, свободная память, размер строк, планы PostgreSQL и перекрытие периодов.
Память memo растёт линейно с числом уникальных identity в одном вызове.
Входные данные и остальные стадии отчёта здесь не измерялись. Защита памяти
и сериализация тяжёлых операций сохранены. Лимиты SQL-пакета не относятся
к лимиту 250 товаров внешнего lookup API, который не изменён.

Обычное обновление кода после проверки PR; миграции и синхронизация не нужны.
После согласованного развёртывания сравнить диагностические счётчики и время
на обычных пользовательских запросах, без нагрузочного теста. Для отката
вернуть этот коммит; данные и схема БД не изменяются. Деплой не выполнялся.
