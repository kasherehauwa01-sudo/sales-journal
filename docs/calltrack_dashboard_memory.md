# Оптимизация dashboard-sales

Задача относится к `POST /api/integrations/calltrack/dashboard-sales`. Исправление
лимита параметров `product-sales/summary` описано отдельно в
`product_sales_large_selection.md`; ранее подготовленные изменения сохранены.
Рабочие БД, контейнеры и репозиторий Calltrack в этой работе не изменялись.

## Подтверждённые данные

Владелец предоставил traceback `asyncpg.DiskFullError` при расширении сегмента
`/PostgreSQL.*` на 4 МиБ. Read-only проверка владельца показала:

- `HostConfig.ShmSize = 67108864`: лимит `/dev/shm` — 64 МиБ.
- На момент проверки занято 2 МиБ, свободно 62 МиБ. Это не измерение пика во время
  ошибки и не доказательство, что увеличение лимита обязательно.
- Файловая система: 37,6 ГБ всего, 33,6 ГБ занято, 4,0 ГБ свободно (89%). Путь
  фактического `data_directory` и отдельные `temp_tablespaces` нужно сопоставить
  с файловыми системами; свободные 4 ГБ не являются бюджетом только PostgreSQL.

Ошибка согласуется с нехваткой POSIX dynamic shared memory при параллельном плане,
например Parallel Hash, но конкретный узел плана ещё не измерен. Отсутствие места
в `/dev/shm` и нехватка места для SQL temp-файлов — разные ограничения. Увеличение
swap не увеличивает размер этого mount; рост лимита tmpfs не исправляет запрос.

## Что изменено

`app/services/calltrack_dashboard.py`:

1. Список клиентов передаётся одним типизированным `VARCHAR[]` через ANY, включая
   выборку из 100 003 имён. Сохраняется исходное SQL-преобразование имени:
   `lower(trim(regexp_replace(client, '\s+', ' ', 'g')))`. Оно не заменяется новым
   алгоритмом сопоставления клиентов или fuzzy matching.
2. Одна узкая PostgreSQL MATERIALIZED CTE содержит только `id`, `sale_date`,
   `total_amount` отобранных продаж. Дата и клиентский scope применяются в ней
   один раз; обе месячные сводки используют этот же MVCC-срез.
3. Заголовки агрегируются по году/месяцу отдельно: выручка и количество чеков.
4. Количества позиций агрегируются сразу по году/месяцу, без промежуточного
   GROUP BY по миллионам sale_id. Обе итоговые сводки содержат максимум 24 группы
   за два года. Их LEFT JOIN не размножает выручку/чеки и сохраняет чеки без позиций.
5. Загрузка scope и расчёт сериализуются с другими тяжёлыми API-отчётами. Пустой
   список менеджеров и отсутствие совпавших клиентов не запускают SQL. Ошибка
   справочника по-прежнему приводит к ошибке, а не к неограниченной выборке.

Общий новый модуль `app/services/report_execution.py` предоставляет контекст
`report_transaction`. Только в транзакции отчёта он устанавливает:

```sql
SET LOCAL max_parallel_workers_per_gather = 0;
SET LOCAL work_mem = '4MB';
SET LOCAL hash_mem_multiplier = 1;
SET LOCAL statement_timeout = '60s';
SET LOCAL lock_timeout = '2s';
```

Транзакция откатывается перед освобождением допуска, включая ошибку и отмену.
Настройки не сохраняются в соединении пула и не меняют defaults сервера.
Нехватка ресурсов/места и тайм-аут возвращают 503 с Retry-After, не фиктивные нули.
В журнал попадают SQLSTATE и класс драйвера, без SQL-параметров. Прочие ошибки не
маскируются. Маршрут, token-auth, DTO, календарные границы/as_of, нормализация
менеджеров, 12 текущих и 12 прошлогодних месяцев и числовой JSON сохранены.

## Ограничения памяти и временных файлов

Серийный план исключает parallel-worker DSM этого запроса. Это не запрет DSM для
других запросов/сервисов. `work_mem` — бюджет на узел, а не жёсткий предел памяти
процесса. Материализованная CTE, private hash/sort и набор массивов всё ещё требуют
памяти; CTE и операции соединения могут сбрасываться во временные файлы. Поэтому
4 ГБ свободного диска нужно наблюдать, особенно при сторонних заданиях.

Малые месячные агрегаты уменьшают кардинальность GROUP BY, однако соединение
позиций с выбранными sale_id остаётся. Без реального плана нельзя гарантировать
индексный доступ вместо сканирования. Требуется проверить существующие индексы
sales.sale_date и sale_items.sale_id и оценку размера scope. Новые индексы, ANALYZE,
VACUUM, серверные настройки и миграции автоматически не создаются.

## Проверки и границы доказательства

Финальный целевой прогон: **143 passed, 1 skipped**. Пропущен тест, требующий
изолированной PostgreSQL `analytics_test`; рабочая БД не использовалась.
`git diff --check` выполнен успешно.

- Численное сравнение старого и нового SQL на SQLite в памяти: два года,
  нормализация пробелов/регистра, несколько клиентов/менеджеров, возвраты,
  нулевые количества, NULL-количества, чеки без позиций, пустой scope,
  граничные даты/as_of и будущие документы. SQL группировки выполняется реально;
  только PostgreSQL ANY адаптирован к малому IN в SQLite.
- Native asyncpg SQL-компиляция: 100 003 имени, один массив, одна regexp_replace,
  постоянное число параметров, отсутствие GROUP BY sale_items.sale_id.
- Проверяются применение локальных лимитов до SQL, rollback при успехе/ошибке,
  последовательность нескольких dashboard-запросов, отсутствие SQL при пустом
  выборе и отказ без фиктивных результатов при DiskFull.
- Cross-repository HTTP-тест использует реальный маршрут, token-auth, DTO и SQL
  с подменёнными справочником/БД; подтверждает контракт текущего Calltrack.
  Синхронный auth worker проверяется вне ограничения песочницы, без production.
- Инспектор плана проверяется отдельно: отсутствие ANALYZE-исполнения, read-only
  транзакция, rollback, отсутствие загрузки клиентов в режиме metadata и
  исключение клиентских литералов из выдачи плана.

Реальный PostgreSQL план, объём spill/DSM и время выполнения на VPS не измерены.
SQLite/компиляция/DB-double не заменяют PostgreSQL integration и нагрузочный тест
при 2 ГБ RAM. Эту версию нельзя объявлять полностью проверенной в production.

## Read-only проверка владельцем

Команды ниже выполняются в обычной оболочке VPS. Сами по себе они не запускают
отчёт, миграцию, пересоздание контейнера или worker.

```bash
docker inspect --type container --format \
  'image={{.Config.Image}} id={{.Image}} project={{index .Config.Labels "com.docker.compose.project"}} files={{index .Config.Labels "com.docker.compose.project.config_files"}}' \
  sales-journal-db
docker inspect --type container --format 'shm_bytes={{.HostConfig.ShmSize}}' sales-journal-db
docker inspect --type container --format '{{range .Mounts}}{{println .Type .Name .Source .Destination}}{{end}}' sales-journal-db
docker exec sales-journal-db df -h /dev/shm /var/lib/postgresql/data
free -m
docker stats --no-stream --format '{{.Name}} {{.MemUsage}}' sales-journal-db sales-journal-backend
```

Подготовлен `backend/scripts/inspect_calltrack_dashboard.py`. Он использует
существующие credentials внутри backend, но не печатает их. Проверенная копия
скрипта подаётся через stdin, поэтому не требуется записывать её в контейнер:

```bash
# Из каталога с проверенной копией scripts/inspect_calltrack_dashboard.py:
docker exec -i sales-journal-backend python -B - \
  < backend/scripts/inspect_calltrack_dashboard.py
```

Без `--manager` читаются только pg_settings, текущие cumulative temp_files/
temp_bytes/stats_reset из pg_stat_database и имена индексов. ClientsVR не
запрашивается, продажи не рассчитываются. Сравните counters до/после отдельного
согласованного одиночного отчёта: они относятся ко всей БД, а не только dashboard.
Изменение stats_reset или активность других запросов мешает атрибуции spill.
Скрипт не сбрасывает counters и не выводит содержимое временных файлов.

После установки оптимизированного query builder можно получить оценочный план:

```bash
docker exec -i sales-journal-backend python -B - \
  --year 2026 --manager '<точное имя менеджера>' \
  < backend/scripts/inspect_calltrack_dashboard.py
```

`--manager` можно повторять для того же scope, что выбран в Calltrack. Скрипт
загружает справочник менеджеров, но не выводит имена клиентов, затем выполняет
только `EXPLAIN (ANALYZE false, FORMAT JSON, SETTINGS)` в READ ONLY транзакции с
планировочным timeout 5 секунд и локальными лимитами нового отчёта. Старый query
builder отклоняется до подключения к справочнику/БД; нельзя принять его план за
проверку новой версии. В выдаче плана остаётся структура/оценки, без Filter/Index
Cond и параметров. Проверяются отсутствие Gather/Parallel Hash, scope-фильтрация
до соединения, две месячные агрегации, ширина CTE и оценка строк join.

Это оценочный одноразовый план через psycopg; он может отличаться от закэшированного
prepared plan asyncpg. ANALYZE не включается. Ни сам dashboard-запрос, ни массовые
COUNT не исполняются этим скриптом. Реальное время, temp spill и пик /dev/shm
проверяются отдельно после разрешения на один контролируемый запуск, без нагрузки
параллельными повторами. Планы с одним случайным клиентом не характеризуют scope
всех выбранных менеджеров.

## Решение по shm_size

Сейчас увеличение **не требуется для внедрения SQL-исправления и не обосновано
измерением пика**. Рекомендация: сохранить 64 МиБ и сначала проверить серийный
оптимизированный запрос и остаточные ошибки по другим endpoint.

Если затем будет измерено исчерпание /dev/shm другими необходимыми параллельными
запросами, оценить 128 МиБ после проверки суммарного RAM/cgroup бюджета. Это
максимум, не предварительное резервирование 128 МиБ; реально использованные
страницы tmpfs увеличивают давление на память. 128 МиБ может лишь сдвинуть предел,
а не устранить избыточные планы/конкурентность. Более высокое значение сейчас
предлагать оснований нет.

Условный пример будущего override, **не созданный и не применённый этой работой**:

```yaml
services:
  db:  # сначала подтвердить фактическое имя Compose-service
    shm_size: 128m
```

Для изменения HostConfig.ShmSize потребуется **пересоздание контейнера PostgreSQL**.
Простой restart размер не меняет. Это означает краткую недоступность БД для всех
зависимых сервисов, обрыв соединений, rollback текущих транзакций и возможные
ошибки/повторную обработку незавершённых импортов и заданий. Нужны согласованное
окно, остановка/дренирование активных операций владельцем и проверенный backup/
restore-план. Существующие volume, PGDATA, PostgreSQL image digest, Compose
project/file order и credentials должны сохраниться: ошибочный проект/volume
может запустить пустую БД. Нельзя удалять volume или использовать down -v.
Миграция данных для одного изменения shm_size не нужна, но риски подключения и
перезапуска остаются. В рамках этого исправления Docker Compose не менялся.

## Передача и обновление

Dashboard-часть: `app/services/calltrack_dashboard.py` и общий новый
`app/services/report_execution.py`. Диагностика и тесты не требуют правок PHP
Calltrack. Предыдущие product-sales изменения не терять и не считать обязательной
частью отдельно рассматриваемой оптимизации dashboard; общий resource helper
должен попасть в оба варианта сборки. Он использует существующий
product_analytics_runtime (heavy_operation/ensure_headroom), наличие которого
нужно сверить в фактическом V3 build context.

Переносить код поверх подтверждённых текущих V3 исходников после сравнения базовых
файлов; собирать backend через существующую CI-сборку, сохраняя серверные функции,
storage, auth и конфигурацию. Сверять digest и контрольные суммы runtime-модулей.
Новые зависимости, модели, миграции, изменение shm_size и пересоздание PostgreSQL
для SQL-исправления не нужны. Нормальный checked startup не заменять старым
alembic upgrade head. Развёртывание backend, запуск реального dashboard и изменение
PostgreSQL-контейнера требуют отдельного разрешения; здесь ничего не запускалось.
