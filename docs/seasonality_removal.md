# Удаление сезонности

Удалены страница и API `/reports/seasonality`, вычислительный алгоритм, агрегация,
планировщик, сохранение сезонных профилей и отдельные benchmark-сценарии. В
«Кандидатах в акцию» удалены сезонные фильтры, показатели, рекомендации, столбцы и
их экспорт. Порядок кандидатов снова определяется количеством обычных причин,
затем стоимостью остатка. Остальные критерии, фотографии, складские остатки,
менеджер, карточка товара и экспорт сохраняются.

## Общие механизмы остаются

`services/source_control.py` содержит прежние PostgreSQL advisory locks и
проверку владения, включая корректное освобождение при отмене. Идентификаторы
734190220, 734190221, 734190117 не изменены: ими пользуются импорт, RFM, сигналы
риска и проверенные updater-скрипты. Зарезервированный worker lock сохраняется
для совместимости и обнаружения ещё работающего старого процесса.

`services/sales_revision.py` и `models/sales_source.py` сохраняют существующий
счётчик `source_revision` в физической таблице `seasonality_state`. Импорт и
удаление продаж по-прежнему инвалидируют RFM/сигналы. Значение счётчика не
сбрасывается. Старые поля модели сохранены для совместимости схемы; новые
изменения продаж больше не планируют сезонный пересчёт.

Два коротких модуля совместимости остаются: `app.seasonality` импортируется
проверенными updater preflight, а `services.seasonality_worker` экспортирует
только общие блокировки и старое имя исключения. В них нет расчётов, обработки
пакетов или планировщика. Любая старая CLI-команда завершается отказом без
подключения к БД.

## PostgreSQL и откат

Новой миграции нет. Launcher, цепочка Alembic, Compose и updater не изменяются;
текущая схема остаётся `20261112_28`. Физические исторические таблицы
`seasonality_months`, `seasonality_store_months`, `seasonality_profiles` не
удаляются. Приложение больше не отображает их в ORM и не читает/не обновляет их.
Это сохраняет данные и возможность отката образов без DDL. Освобождение места
удалением старых таблиц — отдельная разрушительная операция, не часть изменения.
Таблицу состояния со счётчиком нельзя удалять вместе с ними.

## Безопасная установка оператором

1. До переключения образов найти фактический старый процесс сезонности и его
   способ запуска на VPS. Приостановить, остановить и отключить именно его
   расписание/автоперезапуск штатным механизмом. Имена внешних systemd units или
   Compose workers в репозитории не подтверждены; их нельзя угадывать. Пока старый
   worker держит lock 734190221, updater должен отказывать штатным образом.
2. Собрать backend и frontend вне VPS, использовать действующую процедуру
   обновления готовыми образами с резервными образами, locks и healthchecks.
   Для уже установленной схемы 28 миграция не нужна. Для более старой схемы
   сначала применить существующую согласованную процедуру её обновления.
3. Если внешняя проверка SHA256 охватывает затронутые файлы общих импортов,
   провести предусмотренный ручной review нового хеша. Не отключать проверку и
   не менять утверждённые политики, подписи или бюджеты автоматически.
4. Проверить импорт, RFM, мониторинг риска и обычный отчёт кандидатов. Перезагрузить
   открытые вкладки браузера. Старые параметры `use_seasonality` и
   `seasonality_status` отклоняются с 422, а не принимаются молча. Старые API
   сезонности возвращают 404; PDF остальных семи типов отчётов сохраняется.
5. При необходимости вернуть предыдущие backend/frontend образы штатным updater.
   Старые таблицы и счётчик сохранены. Не включать старый сезонный worker
   автоматически при откате; это отдельное действие оператора.

Production, миграции, таймеры, контейнеры и данные этим изменением не затрагивались.
Состояние внешних процессов требует проверки оператором.

## Проверки

Полный доступный backend-набор: 1023 passed, 337 skipped (не настроенные отдельные
PostgreSQL/внешние интеграционные fixtures); cross-repository Calltrack contract
не запускался без соседнего checkout. Frontend: 167 passed, production-сборка
TypeScript/Vite успешна. Дополнительный изолированный PostgreSQL-набор: 52 passed; проверяет
схему 28, сохранность исторических строк, рост общего счётчика, RFM, импорт и
общие locks. Локальный Chromium с подставными API проверяет отсутствие сезонных
элементов, старые настройки колонок, карточку, фото-заполнитель, склад и менеджера.
Никакие реальные API, продажи или email production не использовались.
