# Снижение пика памяти «Кандидатов в акцию»

## Что установлено

Исходная версия main `3ab77a7`: `_sales()` использует `.all()` SQL-результата,
затем строит отдельный список словарей; оба набора одновременно живы на этапе
конвертации. `_catalog()` строит список всех идентификаторов и накапливает
полные вложенные batch-info ответы поверх ограниченного кеша. `_dataset()`
дополнительно создаёт filtered и sorted списки ссылок на те же строки. Это
не полные копии строк, но дополнительные массивы ссылок. Excel создаёт ORM-
подобные объекты всех ячеек обычного Workbook (не SQL ORM).

Только `get_catalog_batch_info()` держал общий heavy_operation: до вызова
каталога и после его возврата тяжёлые стадии разных promotion-запросов могли
перекрываться. Подтверждается границами контекста в services/vrcatalog.py и
отсутствием route_class в исходном promotion_candidates_report.py. Контроль
RAM не предотвращает рост между проверками или аллокацию внешнего процесса.

На синтетическом наборе измеренно подтверждён большой вклад накопления полных
ответов каталога. Production OOM невозможно приписать только этому фактору:
SQL-буферы, другие стадии, кеши и процессы VPS также могли участвовать.
Нет production-замеров отдельного вклада каждого из них.

## Изменения

- `_sales()` использует AsyncResult/server-side cursor, yield_per=250,
  конвертирует строки по мере чтения; курсор закрывается в finally.
- Клиент batch-info получил внутренний необязательный project callback.
  В promotion-результате сразу остаются только категория, бренд, производитель
  и числовой суммарный остаток. Полные ответы переживают только окно HTTP-
  пакетов и существующий ограниченный кеш. Default остальных потребителей и
  кеш по-прежнему содержат полный ответ, включая фотографии/цены/остатки.
- Сохранены прежние внешние границы 5000 идентификаторов, внутренние пакеты 250,
  два worker, порядок merge и код/article aliases. Общая компактная карта
  нужна для точного last-alias-wins при коллизиях между пакетами; немедленное
  обогащение каждой строки без этой карты могло бы изменить старые результаты.
  Карта удаляется сразу после обогащения. Полный список идентификаторов убран.
- Фильтрация выполняется в том же списке и затем стабильная in-place сортировка.
  Порядок равных ключей и все критерии сохранены. Criteria.model_dump один раз.
  Суммирование остатков dict не создаёт отдельный список значений.
- Весь POST отчёта/Excel (включая JSON-кодирование и send) держит существующую
  очередь и файловую блокировку HeavyAnalyticsRoute. Она общая с товарной
  аналитикой в том же контейнере. Лёгкий history и health не входят в очередь.
  Нет новых лимитов, TTL, повышения параллелизма или отключения защиты.
- Excel — write-only Workbook в run_cpu: все строки/листы/значения прежние,
  XML пишется во временные файлы и удаляется при успехе/ошибке RAM. При отмене
  run_cpu удерживает admission до завершения настоящего потока.
- ensure_headroom перед чтением, SQL-пакетами, пакетами каталога, обработкой,
  сортировкой и Excel. diagnostics теперь безопасен и в потоках: дефицит RAM
  даёт HTTP 503, а не RuntimeError отсутствующего event loop.

Изменений схемы, миграций, импорта, синхронизации фотографий нет. Источник
остатков — прежний VRCatalog; локальный каталог его не заменяет, так как
не хранит актуальные остатки. Перевод только характеристик также потребовал бы
проверки иных правил сопоставления/категорий и согласования актуальности.
Без отдельного компактного API характеристик+остатков внешнюю загрузку
полностью исключить нельзя. Неподтверждённые маршруты не используются.

## Измерения

Только синтетические данные, PostgreSQL и HTTP не используются. Холодный
кеш, свежий Python 3.12 процесс для каждого образца, одинаковые 27 016 строк
и богатые batch-info (16 характеристик, 8 цен, 5 складов, фото). Значения всех
результирующих строк и их порядок имеют одинаковые SHA-256. До/после используют
один неизменённый batch-клиент и лимиты кеша, разница — компактная проекция и
обработка датасета. SQL-streaming здесь не измерен: синтетический `_sales`
возвращает одинаковый готовый список обоим вариантам. Его равенство проверено
отдельным SQLite-тестом. JSON-кодирование/сеть/отправка также не входят в замер.

| Сценарий | RSS до, МиБ | RSS после, МиБ | Время до, мс | Время после, мс |
|---|---:|---:|---:|---:|
| 5 000 строк, датасет, один запуск без trace | 127.430 | 90.672 | 1175.805 | 943.050 |
| 27 016 строк, датасет, 3 запуска | 410.379 | 135.812 | 7340.849 | 6979.609 |
| 27 016 строк, датасет + Excel, один запуск | 440.387 | 137.660 | 11496.376 | 11250.430 |

RSS — максимальный абсолютный пик процесса среди запусков; время — медиана,
если запусков три. Это уменьшение пика примерно на 67% для датасета и 69%
для Excel на конкретной структуре. Быстродействие реального отчёта не доказано.
Для 5000 отдельный tracemalloc-запуск: пик Python 63 619 249 → 24 959 692 байт.
Времена traced-запусков не смешиваются с обычными.

HTTP-пакетов для 27 016 товаров: 109 до и после. Кеш: начислено 25 160 205 байт
(меньше 24 МиБ), deep estimate 11 672 433 байта. Оценка включает cache и
словарь размеров, дедуплицирует общие объекты; не включает всю стоимость
аллокатора/интерпретатора и не является отдельным измерением RSS кеша.
Conservative accounting заряжает code/article aliases отдельно, поэтому
здесь кеш не превышал бюджет, но накопленные ответы отчёта жили вне него.
Исходные образцы: docs/benchmarks/promotion_memory_results.json.

Воспроизведение в изолированной среде, НЕ на VPS:

```bash
PYTHONPATH=backend python backend/benchmarks/benchmark_promotion_memory.py --run --rows 5000 --repeats 1
PYTHONPATH=backend python backend/benchmarks/benchmark_promotion_memory.py --run --rows 27016 --repeats 3 --no-trace
PYTHONPATH=backend python backend/benchmarks/benchmark_promotion_memory.py --run --rows 27016 --repeats 1 --no-trace --excel
PYTHONPATH=backend pytest -q
```

Benchmark требует --run, ограничен 30 000 строками и тремя повторами; подменяет
HTTP/SQL, использует отдельный временный admission-файл. Не запускать
одновременно с другими замерами CPU/RSS. Frozen baseline предназначен только
для тестов/замеров и не является вторым production-путём.

## Диагностика и тесты

Стадии promotion_sales/catalog/enriched/classified/excel: время, число строк,
число ключей карты, текущий RSS/swap, доступная RAM, процессный peak RSS,
active/waiters, начисленный размер/число записей кеша, размер Excel.
process_peak_rss_bytes — максимум за жизнь процесса, не отдельный stage peak.
Ключи, имена товаров/клиентов, значения фильтров, токены не логируются.

Регрессии: точное равенство frozen baseline по фильтрам/критериям/сортировке,
5000-границы и межпакетные алиасы, все строки/KPI, тёплый compact/full кеш,
сохранение фото в default-кеше, SQL-агрегаты, закрытие курсора при RAM-ошибке,
Excel все строки/листы/ячейки, очистка XML, 503 из потока и до запуска dataset,
одинаковые/разные параллельные запросы, health/history при занятости, отмена
и повторное admission, безопасные числовые логи.

## Риски и применение

OOM на production не объявляется устранённым. Итоговый список и компактная
карта остаются O(N); особо большие ответы/значения каталога, драйвер, кеши,
несколько контейнеров и остальные процессы могут увеличить реальный пик.
Лимит файла действует в одном файловом пространстве контейнера, не глобально
на все контейнеры. 503 memory_headroom при недостатке RAM — ожидаемая защита.
Частично упавшие batch-info продолжают иметь прежнее поведение клиентского
адаптера; полностью недоступный каталог сохраняет прежний fallback отчёта.

Excel снижает RAM за счёт временного XML на диске: нужны место и права в /tmp.
Буфер готового XLSX/Response остаётся в памяти. Повторные отчёты не получили
новый кеш/single-flight: они сериализуются и используют прежний кеш VRCatalog.
Все строки сохраняются для итогов и Excel; ограничение 300 касается только
прежней таблицы. Отменённый браузерный запрос не обязательно мгновенно
останавливает поток/серверный расчёт.

После проверки PR — обычное согласованное обновление backend; миграции и
изменения Docker/PostgreSQL/Swap не нужны. Проверять обычные запросы и новые
счётчики, не запускать нагрузку на рабочей БД. Быстрый откат — возврат коммита
backend; схема/данные не изменены, но возврат восстановит прежние пики памяти.
Деплой, перезапуск контейнеров и production-запросы не выполнялись.
