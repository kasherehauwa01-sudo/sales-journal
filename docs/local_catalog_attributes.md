# Локальные характеристики CatalogVR: ручная сверка

## Область изменения и совместимость

Только товарная аналитика (`/reports/product-analytics/*`) и её справочники
фильтров переводятся на локальную PostgreSQL-проекцию. Включённый локальный режим
не вызывает CatalogVR при построении отчёта, включая холодный кеш. Исторические
продажи используют текущую успешно полученную проекцию. Импорт, FTP, сценарии,
Docker, PostgreSQL-настройки и защита памяти не меняются. Автоматической
синхронизации нет. Никакие миграции/запросы/деплой на VPS автором PR не выполнялись.

Контракт: [VRCatalog PR #163](https://github.com/kasherehauwa01-sudo/vrcatalog/pull/163),
[`ANALYTICS_LOOKUP_API.md`](https://github.com/kasherehauwa01-sudo/vrcatalog/blob/main/ANALYTICS_LOOKUP_API.md).
API возвращает `category` (родитель) отдельно от `legacy_category` (старое
значение `batch-info.category`). Чтобы сохранить группировки, отчёт использует
**legacy_category**; оба поля сохраняются. `subcategory` — XML-раздел.
`updated_at` сохраняется для диагностики, но никогда не служит курсором сверки.

Новый API не отдаёт фотографии, цены, остатки и полный список свойств. Эти
данные по-прежнему загружаются через прежний `batch-info` только при явном
открытии подробной карточки. Расчётный датасет больше не содержит эти тяжёлые
вложения; соответствующие существующие поля ответа остаются пустыми массивами
до загрузки карточки. Фотографии, полученные при открытии карточки, сохраняются
как URL и используются в следующих отчётах. На холодном справочнике таблица
показывает существующий placeholder; массового автоматического прогрева фото нет.
Data-URI и URL длиннее 8192 символов не сохраняются в справочнике, но могут
отображаться в самой карточке. Это явное ограничение первого этапа.

При `not_found`/`ambiguous` ранее сохранённая проекция не удаляется, но не
используется для этого сопоставления. Сетевой сбой сохраняет прежний статус и
проекцию. Успешный `matched` заменяет характеристики полностью, включая NULL.
Отсутствие значения отображается как «Не заполнено» по прежним правилам.
Дополнительные `catalog_status`, `catalog_synced_at`, `horeca` в товарных строках
и `catalog` в полном отчёте дают диагностику без изменения финансовых расчётов.

Нельзя гарантировать прежний случайный выбор для дублирующегося артикула:
новый API специально возвращает `ambiguous`. Такой товар остаётся в финансовых
итогах без выдуманных характеристик. Активный фильтр характеристик может его
исключить, как и другие товары без характеристик. Панель предупреждает о неполном
проходе, таблица — о статусах сопоставления; отчёт возвращает покрытие оставшихся
после фильтров строк. Неполный справочник нельзя считать полностью корректным
источником фильтруемого отчёта.

## Хранение

* `catalog_products`: PK — стабильный ID товара CatalogVR; только необходимые
  характеристики, source timestamp, время успешного получения и необязательный URL.
* `catalog_lookups`: PK — SHA-256 нормализованной пары `(code, article)`; FK на
  проекцию, статус, способ сопоставления, время проверки, цикл сверки. Уникальности
  артикула/кода нет. `strip/casefold`, ведущие нули и символы сохраняются; числовые
  идентификаторы не преобразуются в строки. Пустые/слишком длинные идентификаторы
  помечаются `invalid`, никогда не обрезаются и не отправляются в API.
* `catalog_sync_state`: одна строка, checkpoint ID позиции продажи, верхняя граница
  прохода, номер цикла, ревизия кеша, статусы/счётчики/времена.

Исходные `Sale`/`SaleItem` не меняются, новых FK в миллионах позиций нет.
Чтение для отчёта — пакетами по 250 пар, без загрузки всего справочника.
Один REPEATABLE READ snapshot на отчёт согласует ревизию и все страницы;
синхронизатор не блокирует строки отчёта. Это настройка отдельной транзакции,
не изменение PostgreSQL-конфигурации. Длительные отчёты могут удерживать MVCC
снимок; следует контролировать длительность/вакуум на стенде.

Одинаковые нормализованные коды с разными артикулами могут схлопнуться в прежний
ключ отчёта. Если их локальные сопоставления конфликтуют, характеристики
маркируются неоднозначными. Прежний финансовый алгоритм слияния не исправляется
попутно; отдельный аудит таких исходных продаж остаётся необходимым.

## Ручной запуск и продолжение

Команда запускается **оператором** в подготовленном backend-окружении:

```bash
python -m app.catalog_sync status
python -m app.catalog_sync run --max-products 100 --max-scan-rows 1000 --batch-size 100
```

Значения по умолчанию: 1000 уникальных проверок/10000 прочитанных позиций за
вызов, пакет 100. Жёсткие максимумы: 10000 проверок/100000 позиций за вызов,
пакет 250. Для VPS начинать с меньшего разрешённого объёма после стендовой проверки.
Уникальные пары повторно не проверяются в одном цикле; идентификаторы продаж
читаются по PK (`id > cursor ORDER BY id LIMIT ...`), не глобальным DISTINCT
по 4,6 млн строк. За один запуск чтение всегда ограничено, даже если продажи
содержат миллионы повторов.

Сессия advisory-lock в PostgreSQL не допускает второй CLI-запуск, в том числе
в другом worker/контейнере той же БД. Это отдельный nonblocking lock, не lock
аналитики. Сетевые запросы последовательны; один клиентский слот. Каждый
пакет фиксирует данные, ревизию и checkpoint одной короткой транзакцией.
Во время HTTP нет открытой транзакции с записями. Глобальной публикации полного
снимка нет: API не предоставляет snapshot; отчёты видят последние успешно
зафиксированные данные на начало своей транзакции.

Повторная команда продолжает незавершённый цикл. Когда достигнута верхняя граница,
цикл завершён; следующая ручная команда начинает полный новый проход с нуля,
включая новые импортированные позиции. Повторная проверка учитывает изменения
категорий без изменения `updated_at`. Новые продажи за уже зафиксированной верхней
границей попадут в следующий цикл; существующие импорты не изменяются.

SIGINT/SIGTERM устанавливают остановку после текущего пакета. HTTP: таймаут 15 с,
до трёх попыток, backoff 0,5/1 с. 401/403/422 и ошибки схемы не повторяются;
429 учитывает числовой Retry-After до 5 с, более долгий лимит завершает попытку
для последующего ручного запуска. Ответ ограничен 8 MiB; слишком большой ответ
не применяется и данные не обрезаются. Принудительное завершение процесса
может оборвать пакет, но checkpoint не продвинется без commit. Повторный пакет
безопасен. Уже начатый HTTP-поток при отмене дожидается завершения.

Перед страницей проверяется существующий запас RAM 256 MiB; отказ фиксирует
`memory_headroom`. Пакеты/списки/ORM-объекты освобождаются между страницами.
Кеш аналитики остаётся: TTL 120 с, 2 записи, 32/48 MiB. Его ключ включает
сохранённую ревизию справочника; она инвалидирует результат между worker-процессами.
Синхронизация не запускает тяжёлый пересчёт отчёта.

## Мониторинг и пределы полноты

`GET /api/reports/product-analytics/catalog-status` и CLI `status` возвращают
счётчики discovered-идентификаторов, прогресс курсора, последнюю успешную запись
пакета (`last_success_at`), последнюю полную сверку (`last_full_success_at`),
ошибку фиксированным кодом и время начала/окончания последнего запуска.
Счётчики state накопительные; результат CLI и логи содержат счётчики одного вызова.
`stale_records` — matched-пары с последним успешным lookup старше 30 дней;
это диагностика, не TTL и не отключение ранее успешных данных.
`unsynchronized_records` — известные pending-пары. Ещё не прочитанные продажи
**не включаются** в это число: точный глобальный DISTINCT ради открывания страницы
не выполняется. `completed`, `cursor`, `upper_id` показывают границы охвата.
`has_unscanned_sales` выявляет позиции, импортированные после зафиксированной
верхней границы, через дешёвый MAX(id) по PK; это не глобальный COUNT/DISTINCT.
Не приравнивать `last_success_at` к полной сверке.

Логи: только числа, длительность, фиксированные статусы/коды; без идентификаторов,
характеристик, персональных данных, токенов, URL и полных exception/payload.
Публичная диагностика не содержит товарные идентификаторы или тела ошибок.

## Порядок последующего развёртывания оператором

1. Проверить/согласовать PR и сохранить текущий backend revision/image.
2. На изолированном стенде установить `backend/requirements-test.txt`, выполнить
   тесты, проверить Alembic upgrade/downgrade и малый ручной проход с тестовым API.
3. **Учесть текущий Dockerfile:** обычный старт backend выполняет
   `alembic upgrade head`. Не считать рестарт разрешённым обходом запрета миграций.
   Перед production-рестартом отдельно согласовать миграцию и проверить все
   pending revisions; не запускать обновление всех сервисов.
4. После согласования оператор применяет миграцию `20261010_15`. Она только создаёт
   три таблицы и индексы, без сканирования/изменения продаж и сетевых запросов.
5. Для постепенного перехода оператор может оставить
   `PRODUCT_ANALYTICS_LOCAL_CATALOG_ENABLED=false`: действующий batch-info путь
   остаётся доступен. Новое значение по умолчанию — true; поэтому перед первым
   deploy нужно явно выбрать режим, чтобы не получить неполный локальный отчёт.
6. Выполнить малые ограниченные CLI-проходы; проверить статусы и довести нужный
   охват до полного цикла. Не включать cron/scheduler автоматически.
7. Проверить характеристики и финансы на согласованном малом наборе; переключить
   локальный режим. Убедиться, что холодный report не вызывает CatalogVR,
   а подробная карточка по-прежнему показывает фото/цены/остатки.

Автор PR ничего из production-шагов не выполняет.

## Откат

Быстрый функциональный откат: оператор устанавливает
`PRODUCT_ANALYTICS_LOCAL_CATALOG_ENABLED=false` и штатно перезапускает только
backend после согласования. Ключи кеша разных источников разделены. Можно вернуть
предыдущий image/revision; новые таблицы не мешают старому коду. Сохранить данные
справочника для диагностики. Удаление таблиц через Alembic downgrade — отдельное
решение оператора после остановки ручной синхронизации, не обязательный шаг отката.

## План остальных потребителей — без изменений в этом PR

| Потребитель | Следующий этап |
| --- | --- |
| Кандидаты в акцию | Локальные характеристики + отдельный проверяемый источник остатков; до его появления сохранять batch-info и классификацию |
| Сценарии HoReCa | Проверить boolean HoReCa и порядок фильтрации, обеспечить фото; не менять FTP/расписание/SMTP попутно |
| HoReCa images | Сохранять текущий поиск изображений, пока локальные URL не покрывают потребителя |
| Аналитика категорий | Сравнить category-map с legacy_category и категорийным JOIN; проверить NULL/not_found и уникальные чеки до переключения |
| Продажи по товарам / CatalogPicker | Нужны непроданные товары, дерево и глобальные значения; sales-only справочник не эквивалентен всему Catalog |

## Изолированная проверка

```bash
python -m pip install -r backend/requirements-test.txt
PYTHONPATH=backend python -m pytest backend/tests
cd frontend
npm ci
npm test
npm run build
```

Новые DB-тесты используют SQLite в памяти, HTTP замокан. Они не импортируют
startup приложения, не подключаются к production PostgreSQL и не вызывают
реальный CatalogVR. PostgreSQL-специфичная блокировка проверяется через mock;
DDL Alembic — через offline SQL и SQLite-исполнение самого нового revision.
Реальные PostgreSQL isolation/advisory-lock нужно подтвердить на стенде до deploy.
Известные старые ошибки тестов get_catalog_tree из-за повторных определений
в vrcatalog.py не исправляются в этом PR.

Тесты доказывают сохранение финансовых значений на фикстурах и отсутствие
CatalogVR-вызовов из локального расчёта. Они не являются production-замером
скорости/пика RAM или проверкой реального PostgreSQL advisory-lock/isolation.
