## Данные и исторические правила

Миграция `20261109_26` после `20261030_25` создаёт девять небольших metadata-таблиц:

- `import_departments`: постоянный ID, уникальный code, текущее отображаемое имя.
- `import_expectation_rules`: интервалы **дат продаж**, display_name на интервале,
  точное имя / один `{date}`, date_format `dmy` или `iso`, active и controlled.
- `import_control_audit`: субъект, поле/старое/новое значение, actor, время, effective_date.
- `import_control_config`: утверждённая дата начала, legacy-поля смещения/marker (не используются),
  получатели, revision; enabled/automatic/email_enabled по умолчанию **false**.
- `import_control_cycles`: начало/окончание, день продаж, статус, доказательство
  окончания источника, revision настроек; упавший владелец отмечается interrupted.
- `import_control_receipts`: связь с существующим ImportBatch, исходный basename,
  SHA256, период/его метод, статус, ограниченный список подразделений, duplicate_of.
- `import_day_checks`: последний результат даты, счётчики, время/код причины.
- `import_control_issues`: уникальные (sales_date, department_id), обнаружение,
  последнее состояние, устранение/административное закрытие с причиной.
- `import_control_notices`: outbox и история отправки, уникальный fingerprint проблем,
  попытки/состояние/время/безопасный код ошибки.

Правило меняют **с даты вступления**: прежний интервал заканчивается накануне.
Отключение сегодня сохраняет вчерашние ожидания и уже обнаруженные пропуски.
Draft с той же датой можно исправить до проверок; проверенный интервал нельзя
молча перезаписать. Дата окончания включительна. Имя в старом issue — снимок.
Физического DELETE API нет; FK RESTRICT сохраняют историю.

Глобальная transaction advisory lock734190270 и PostgreSQL trigger исключают
пересекающиеся интервалы одного подразделения и потенциально одинаковые имена
активных контролируемых подразделений. Поддерживается точное имя или один `{date}`;
произвольных regex/glob нет. Проверка пересечения консервативна: возможно отклонение
формально несовместимых календарных дат, но неоднозначный файл никогда не засчитывается.
Имена NFC, регистр сохраняется (FTP может быть case-sensitive); пути и управляющие
символы отклоняются. `EROOR_` — служебный префикс существующего импорта.

## Проверка и доказательство окончания

[check_date](../backend/app/services/import_control.py) сравнивает правила активной
даты с receipts. Объявленный период предпочтительнее наблюдаемого; успешный файл
с одним наблюдаемым днём допустим. Один диапазон min/max наблюдаемых продаж без
подтверждённого периода не доказывает наличие каждого промежуточного дня: статус
«Проверка недоступна». Корректный нулевой HTML-отчёт с проверенной преамбулой считается
успехом; нулевой размер, ошибка parser/валидатора, ошибки строк — нет. Неизвестный
период корректного пустого файла — недоступность проверки, а не повреждение.

Receipt сам по себе не заменяет успех ImportBatch. Последующая ошибка новой версии
файла видна, поздний успешный штатный импорт разрешает пропуск с сохранением audit.
Зависшая старая попытка не блокирует успешную новую версию бесконечно. Незавершённые
актуальные queued/processing не позволяют объявить завершение и отправить письмо.

## Согласованный срок ожидания: 23:40 → 00:20 МСК

По решению оператора выгрузка1С происходит в23:40, а файлы за эту дату продаж
ожидаются до00:20 **следующего** дня по Москве. Внешний marker не нужен.
До00:20 отсутствие файла не создаёт issue или email, даже при ручном подтверждении.
В00:20 и позже выполняется завершающий проход штатного FTP-импорта: он подбирает
файлы, появившиеся после обычного запуска23:55. Только после завершения прохода и
всех его штатных повторов вычисляется неполнота. Обрабатываемый файл остаётся в
ожидании; ошибка FTP означает недоступность проверки, а не доказанное отсутствие.

Срок фиксирован в Europe/Moscow, независимо от timezone ОС и браузера. Обычный
вечерний проход относится к текущей дате продаж, проход после полуночи — к предыдущей.
День запуска и день продаж не смешиваются; legacy day_offset больше не управляет ими.
Существующий scheduler проверяет наступление срока раз в минуту; при занятом импорте
проверка откладывается до освобождения, а не объявляет ложный пропуск. После рестарта
пропущенный завершающий проход подхватывается этим же scheduler. Повторный завершённый
проход за ту же дату не запускается. Нового сервиса/cron и отдельного восстановления
пропусков нет. Поздний файл обрабатывается обычным импортом и разрешает открытый issue.

Контроль и email остаются выключенными по умолчанию. Поля marker_template и day_offset
сохранены для совместимости схемы/API, но не участвуют в определении срока. Настройка
и ручная проверка не загружают файлы; дополнительный deadline-проход — часть штатного
FTP scheduler и работает только при включённом автоматическом контроле.

Статусы: waiting / complete / incomplete / error / unavailable. Complete невозможен
при отсутствии правил, неизвестном периоде, ошибке цикла или незавершённой загрузке.
До утверждённой start_date проверки не создают историю проблем. Наступление нового
дня не удаляет issues. При административном закрытии сохраняется реальный дневной
результат неполноты, но проблема исключается из открытого уведомления и новой рассылки.

Проверка в UI ограничена31 днём за запрос, выдача истории —50 записей на страницу.
Автоматическое обслуживание в **существующем** scheduler раз в минуту проверяет до5
старейших открытых дат и до5 законченных циклов с потерянным postcheck, затем максимум
одно письмо. Нет отдельного сервиса, daemon, повторного чтения файлов или Sales scan.
Пределы fail-closed:1000 действующих правил,5000 относящихся receipts за дату,
200 записей предварительного списка. Достигнутый предел не превращается в complete.

## Дубли и ошибки

SHA256 считается потоково блоками64КиБ один раз на файл; bytes в БД не сохраняются.
Совпавший hash фиксируется как повтор внутри исходного имени, но не служит глобальным
запретом импорта разных подразделений. Защита от повторного включения продаж остаётся
действующей fingerprint/legacy fingerprint + UNIQUE в sales.

Когда контроль включён, session advisory lock на исходный basename исключает гонку
ручной загрузки с FTP. Конкурирующая попытка завершается контролируемой ошибкой.
[revision_guard](../backend/app/services/import_control_worker.py) не позволяет исправленной
версии контролируемого файла пересекающегося подтверждённого периода создать новые продажи
из-за другого amount/fingerprint. Учитываются и частично сохранённые строки прежней
неуспешной попытки. Исправленная версия требует административной проверки существующей
политики переимпорта; автоматической замены/удаления продаж нет. Для постоянного имени
без подтверждённого периода изменившееся содержимое также требует проверки, иначе
невозможно доказать, что это новый день. Если прежний импорт того же источника уже сохранял продажи, но не имеет hash receipt,
пересекающийся/неизвестный период также отправляется на ручную проверку. Неизменность
старого файла без сохранённого hash доказать нельзя. Для первого включения лучше
утвердить будущую дату и заранее накопить receipts штатного импорта с контролем OFF.
Отключённый контроль не меняет прежнюю политику. Защита относится к утверждённой
идентичности источника; произвольно переименованный неподконтрольный файл не получает
статус ожидаемого и остаётся в прежнем механизме импорта, без новой политики замены.

Ошибка скачивания фиксируется в существующем журнале и failed receipt; для неё дата
опирается только на явно утверждённую целевую дату цикла. Успех таким способом не
доказывается. Отмена/перезапуск не создают фиктивного успешного receipt.

## Email и безопасность

Outbox создаётся только для подтверждённого законченного цикла с открытыми проблемами
и включённой рассылкой. Fingerprint включает дату и точный набор проблем; повторная
проверка того же набора не дублирует письмо. Изменившийся набор может создать новое
письмо. Перед отправкой состояние проверяется заново, устаревшая очередь отменяется.
Устранение само по себе письма не создаёт. Получатели валидируются существующим parser.

MAIL session lock734190272, FOR UPDATE SKIP LOCKED и commit sending перед SMTP защищают
от параллельной отправки. FTP session lock734190271 сохраняет один владеющий цикл;
существующие SOURCE/WORKER/CATALOG locks не заменяются и не отключаются.

Подтверждённые временные отказы SMTP повторяются максимум3 раза с backoff; отсутствие
SMTP тоже ограничено3 попытками. Постоянный отказ не повторяется автоматически.
Disconnect, потерянный ответ, частичная доставка и процесс, оставивший sending,
отмечаются **uncertain**, а не sent. SMTP не гарантирует exactly-once после потери ACK:
оператор проверяет серверный SMTP-журнал и лишь затем запрашивает ручной повтор с
причиной, понимая риск дубликата. Реальные адреса/пароли/сырые строки продаж не
пишутся в новые логи. В БД остаются административный audit и необходимые тексты писем.

Все API защищены существующим require_settings_admin и доступны только через сессию
настроек. Анонимный прямой HTTP не обходит UI. При общей парольной сессии персональное
имя администратора установить нельзя: actor=`settings-admin:shared-session`.
Доверенный mTLS serial используется лишь при правильном proxy secret + SUCCESS.
Переход к индивидуальным пользователям не изобретается в этой задаче.
