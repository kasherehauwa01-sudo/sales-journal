# Фотографии в PDF без глобального CORS

## Причина и реальные источники

На c7659b1 обычный `<img>` может успешно показывать внешнюю фотографию, но Canvas,
куда она нарисована, становится tainted. `canvas.toDataURL()` бросает SecurityError.
Заголовка CORS на сервере недостаточно, если сам `<img>` загружался без anonymous
CORS. Кроме того, прежний `Promise.all(img.decode())` прерывал весь PDF при одной
битой фотографии. Это отдельная проблема от проверки снимков PR172.

Код источников:

- `services/catalog_lookup_client.py:LookupProduct.image_url` принимает необязательный
  URL нового analytics lookup. `catalog_sync.save_results()` сохраняет непустую
  нормализованную ссылку в `CatalogProduct.image_url`.
- `services/catalog_attributes.py:local_catalog()` передаёт сохранённую ссылку
  аналитике. `remember_detail_image()` сохраняет дополнительно найденное фото.
- `services/vrcatalog.py:catalog_item_image_url()` извлекает URL из разных форматов
  batch-info/search. `_absolute_image_url()` привязывает относительные media-ссылки
  к публичному корню CatalogVR (`https://kvasmix.ru/vr/catalog/` при стандартной
  настройке), а не к Sales Journal или корню сайта. Абсолютные ссылки могут вести
  на другие домены. `get_catalog_images()` возвращает ссылки, не бинарные файлы.
- Кандидаты получают `image_url` из компактных данных batch-info/local catalog;
  `components/ProductPhoto.tsx` выводит обычный lazy `<img>`.
- Общедоступного HTTP image-proxy в Sales Journal нет. Есть защищённый загрузчик
  Excel `services/promotion_selected_export.py`: публичные DNS/IP, pinned HTTP/TLS,
  отключённый environment proxy, лимиты размера/пикселей. Его транспорт повторно
  используется для PDF; поведение XLS не изменено.

Фактические URL production-базы не выгружались. Выводы основаны на путях кода;
неизвестные CDN не добавлены в серверный allowlist без подтверждения.

## Обработка

1. Frontend кодирует доступный уже загруженный `<img>` в миниатюру до192×144.
2. Если чтение запрещено, пробует anonymous CORS-загрузку без credentials к
   внешнему домену и без referrer. Попытки последовательные, ≤350мс на фото,
   ≤3с на весь экспорт. Повторяющиеся источники используют общий результат.
3. Оставшийся HTTP(S) URL переносится в служебный `data-pdf-image` в копии DOM.
   Некорректная ссылка сразу заменяется на «Фото недоступно». Живой DOM не меняется.
4. Существующий POST `/api/reports/pdf`, внутри прежнего heavy_operation, разрешает
   серверное получение только доверенных статических изображений CatalogVR.
   После обработки HTML содержит только embedded data:image; Chromium остаётся
   offline, CSP запрещает внешние ресурсы, запросы браузера по-прежнему abort.
5. Ошибка/запрет/исчерпание бюджета отдельного фото даёт «Фото недоступно». Строки,
   показатели, фильтры, детализации и SVG-графики не удаляются. Проверки снимков,
   чисел, totals и неполных данных из PR172 не изменены.

## Серверный allowlist и SSRF

Разрешён только HTTPS origin из серверного `settings.vrcatalog_api_url`, с тем же
портом, и публичный каталоговый корень без `/api` + одна из папок:
`media/`, `uploads/`, `static/`, `images/`, `storage/`.
При стандартной настройке: `https://kvasmix.ru/vr/catalog/<папка>/...`.
Чужие домены, другие проекты, API, userinfo, нестандартные порты, traversal и
повторное percent-encoding не разрешены. Смена домена только в административной
интеграции, без изменения серверной настройки, не расширяет этот allowlist.

Перед соединением все DNS-ответы должны быть глобальными публичными IP; специальные/multicast/IPv6-transition адреса также отклоняются. Соединение
закрепляется за проверенным адресом, SNI/проверка TLS остаются исходного hostname.
Редиректы не автоматические: максимум3попытки, каждый переход снова проходит
allowlist/DNS; нельзя уйти на внутренний адрес, другой домен/проект или HTTP.
Заголовки исходящих запросов — только Accept/User-Agent; Bearer-токен, cookies,
входящие headers и environment proxy не используются. URL/данные не логируются.
DNS имеет ограничение ожидания1с, один worker и защиту от очереди за зависшим DNS.

Нового общего GET image-proxy нет, возможности запросить произвольный URL из
Chromium нет. Внешнее фото с разрешённым CORS может встроить браузер; внешнее фото
без CORS вне allowlist становится заполнителем. Нельзя добавлять произвольный
пользовательский host в allowlist для обхода CORS.

## Ресурсы

- Старые guards памяти/сериализации и лимиты PDF не повышаются.
- Backend: последовательные миниатюры, общий бюджет12с, ≤500уникальных источников,
  ≤2МиБ исходного файла, ≤16МиБ суммарного скачивания (+один блок64КиБ), ≤4млнпикселей, ≤4МиБ суммарных embedded данных.
- Повторные вставки тоже учитываются в общем объёме, включая повторы из кеша.
- Frontend: до500закешированных источников, ≤4МиБ embedded данных; снимок не несёт
  полноразмерных растров с огромными canvas.
- На диске один временный исходный файл ≤2МиБ. Он удаляется после каждого фото;
  каталог удаляется в finally. Кеш существует только в текущем экспорте.
- Нехватка RAM остаётся контролируемой503, не маскируется ошибкой фотографии.
- При медленном источнике/исчерпании бюджета часть фотографий может стать
  заполнителями. Это не ограничивает число товаров или расчёты.

HTTP-сервер с CORS и без CORS, недоступная фотография, некорректный URL и доверенный

размер/MIME/пиксели, отсутствие токенов в headers, квоты, повторы и memory guard.

## Развёртывание и оставшиеся ограничения

Нужны **оба образа: frontend и backend**, собранные вне VPS из согласованного
коммита. Backend первым (понимает новый маркер), затем frontend; до обновления
frontend старый код может всё ещё выдавать CORS-ошибку. Миграций/изменений БД нет,
схема20261030_25 совместима. Использовать имеющийся безопасный updater с готовыми
образами и сохранёнными rollback tags; не собирать Docker на VPS.

После review/merge/отдельного решения оператора проверить реальный отчёт с фото
и без фото, один внешний источник без CORS, число строк/итоги. Нельзя считать
синтетические тесты гарантией отсутствия OOM на любом production PDF.

При откате обоих компонентов возвращается прежняя CORS-ошибка. При откате только
backend новый frontend продолжит отправлять маркер, но старый sanitizer удалит
его, так что фото могут пропасть; необходим согласованный откат пары образов.
Не удалять rollback образы/volumes, не менять глобальный CORS, не открывать network
в Chromium. Production в рамках задачи не изменяется.
