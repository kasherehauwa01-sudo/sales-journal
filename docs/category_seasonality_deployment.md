# Безопасная установка snapshot/schema29 (только оператором)

Никаких команд из этого документа агент на FirstVDS не выполнял. Миграция
20261114_29 только создаёт пустые таблицы и singleton; не сканирует историю,
не запускает расчёт, не меняет SMTP/FTP/уведомления/политики и продажи.

## До окна обслуживания

1. Проверить фактический HEAD и схему. Разрешён переход только
   20261112_28 → 20261114_29 (либо повторная проверка уже29). Launcher по умолчанию
   требует29; обычный start только проверяет схему, не выполняет миграцию.
2. Подготовить проверенную резервную копию отдельно. Сохранить immutable ID
   предыдущих backend/frontend, полный эффективный Compose и все серверные
   overrides/mounts (Calltrack, churn, report-fix, mTLS) в прежнем порядке.
3. Собрать готовые backend/frontend образы на отдельной машине, не на FirstVDS.
   Проверить импорт app.main и launcher --check-only на изолированной копии схемы29.
4. Не запускать действующий schema28 updater с флагом старой миграции: его
   разрешённые ревизии/пин launcher не рассчитаны на29. Для production требуется
   reviewed release/updater manifest29, сохраняющий существующие flock, шесть
   advisory locks, immutable images, backups, image-ID/health и frontend-only
   rollback. Текущий рабочий серверный скрипт этой задачей не заменяется и его
   актуальное содержимое здесь не было предоставлено. Нельзя угадывать overrides.
   Эта проверка является обязательным этапом перед production-установкой.
   Если внешние SHA256 allowlists покрывают изменённые launcher/ClientsVR-файлы,
   обновлять только reviewed release manifest; не отключать проверки целостности
   и не менять утверждённые бизнес-политики/подписи/бюджеты автоматически.

## Окно обслуживания

Использовать согласованную процедуру готовых образов: общий flock и шесть
PostgreSQL locks одной guard-сессии на всё переключение, приостановка фоновых
операций/импорта, остановка старого backend до DDL. Без этих условий следующие
команды не являются самостоятельным скриптом обновления.

В одноразовом контейнере **нового закреплённого backend image**, с той же полной
Compose-цепочкой, секретами/mounts и выключенной automation, выполнить:

```bash
python -B /app/start_backend.py --migrate --expected-revision 20261114_29
python -B /app/start_backend.py --check-only --expected-revision 20261114_29
```

Первый процесс разрешает только reviewed source28/target29, берёт schema lock,
проверяет полученные таблицы/ключи/CHECK/index. Повтор на29 только проверяет,
не запускает повторное заполнение. При любом сбое сначала проверить фактическую
alembic_version и schema preflight. Не stamp/downgrade. Миграция PostgreSQL
транзакционна; нельзя предполагать версию по коду возврата внешнего скрипта.

Переключить backend на новый immutable image ID и обычный launcher29, проверить
/api/health, schema29, runtime ID/entrypoint и effective Compose. Затем отдельно
frontend и /vr/sales/. При неудаче frontend вернуть только frontend, не откатывая
исправный backend. Сохранить recovery-файлы до подтверждённого успеха всех проверок.

После установки API пока отвечает uninitialized, пользователь видит «Отчёт ещё
не рассчитан». Рестарт/посещение страницы не читают исходные продажи для расчёта.

## Первое заполнение — отдельное решение администратора

Сначала оценить запас RAM/диска с учётом совместной кардинальности, двух старых
версий, строящейся версии, WAL и SQL temp. Тестовые11,4МиБ не прогноз production.
Выбрать время без импорта/других тяжёлых задач. Снять внешние updater guard locks
после окончания обновления, иначе построитель правильно ответит busy.

В том же новом backend image и действующей конфигурации:

```bash
python -m app.category_seasonality fill --confirm
```

Это пример команды **внутри** контейнера, а не предполагаемый docker exec с
выдуманным именем. Фактическую команду запуска закрепляет оператор через текущую
Compose-цепочку. Процесс sequential/bounded, nonblocking locks и headroom сохранены.
При busy не было расчёта; повторить вручную в подходящее окно. При ошибке не выдаются
частичные данные; безопасный код ошибки хранится, предыдущий снимок сохраняется.
Не использовать агрессивный shell retry loop. Остановка SIGTERM/отмена откатывает
текущую data-транзакцию; при жёстком обрыве следующий владелец зафиксирует interrupted.

Успешное первое заполнение включает недельный цикл на ближайшую будущую субботу
19:00 МСК. Убедиться, что время устраивает администратора. Автоматическая ошибка
не повторяется в ту же неделю; ручное fill --confirm разрешено осознанно.
Проверить last_success, последний пригодный месяц, next_update, контрольные суммы
фактов на выборке, две подкатегории и быстрые фильтры. Не менять FTP/SMTP для теста.

## Откат без удаления данных

- До изменения схемы вернуть сохранённые предыдущие образы штатной процедурой.
- После29 старый launcher28 самостоятельно не стартует. Использовать **новый
  проверенный launcher29**, смонтированный read-only в прежний закреплённый
  backend image, с `--rollback --expected-revision 20261114_29`. Он импортирует
  код старого image из /app, но проверяет замороженный физический контракт29
  независимо от старых ORM. Lifespan OFF отключает все планировщики в maintenance.
- Не монтировать весь новый backend поверх старого образа. Сверить SHA256 launcher,
  фактический image ID, effective Compose и entrypoint. Сохранять guard/flock и
  исходные overrides, проверить health и состояние maintenance до снятия marker.
- Вернуть frontend отдельно. Не удалять новые таблицы/снимки, volumes, историю,
  серверные конфиги и резервные образы. Downgrade миграции намеренно запрещён.
- Maintenance rollback не равен возвращению автоматических фоновых операций:
  обычный режим требует новой совместимой сборки29 и отдельного успешного
  переключения/проверки. Если автоматический rollback не прошёл, оставить recovery
  и резервные файлы, не продолжать переключения наугад.

Оператору до production нужны: проверка актуального updater29/Compose на сервере,
подтверждение резервной копии, фактический запас диска/RAM, доступность каталогов
ClientsVR в безопасных границах и согласование первого заполнения/weekly schedule.
