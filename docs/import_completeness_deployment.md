# Установка контроля импорта: только согласованное обслуживание

Эти действия **не выполнялись** на VPS. Ветку нельзя устанавливать обычным рестартом
backend на схеме25: новый default launcher ожидает **20261109_26**. Сборка только вне VPS;
обновляются **backend и frontend**, новые зависимости для production не добавлены.

## До миграции

1. Утвердить окно обслуживания, проверенную внешнюю резервную копию и возможность
   восстановления. Не пытаться создать11ГБ backup на сервере с несколькими ГБ места.
2. Зафиксировать actual revision25, immutable IDs работающих backend/frontend и
   предыдущих образов, effective command/mounts и всю существующую цепочку Compose.
   Сохранить её исходные файлы и управляемый image override с правами оператора.
   Не выводить .env, полный config/inspect, SMTP и Calltrack secrets в лог.
3. Доставить проверенные готовые образы для архитектуры VPS штатным механизмом;
   подтвердить ID/digest, свободный диск и RAM. Не выполнять Docker build/prune,
   удаление rollback images, volumes, данных импорта или других проектов.
4. Подготовить **до DDL** локальную неизменяемую копию launcher из нового образа,
   её SHA256 и права чтения контейнером. Указать абсолютный путь в
   SALES_ROLLBACK_LAUNCHER и зафиксировать SALES_ROLLBACK_IMAGE. Проверить rollback
   на изолированной копии схемы26 со старым образом. Замена только image со старым
   launcher25 после DDL **не работает**.
5. Проверить фактический production updater. Доступные исторические инструкции
   перехода24→25 не доказывают поддержку26. Если он жёстко ожидает25, использует
   `--migrate-24-to-25` или откатывает старый launcher без bridge, **не запускать его
   для этого релиза**. Нужна отдельно проверенная адаптация процедуры готовых образов.
   Данный PR не меняет серверный update_sales.sh и не выдаёт его за проверенный live.
6. В согласованном окне дождаться завершения штатного импорта и его повторов,
   исключить новые ручные загрузки; приостановить соответствующих producers/timers
   только по действующей процедуре. Сохранить прежние SOURCE/WORKER/CATALOG,
   updater PostgreSQL locks и flock. Не менять бюджеты, подписи или политики Calltrack.

## Явная миграция25→26

Обычный запуск приложения не выполняет Alembic. Новый launcher допускает только
25→26 или26→26 (во втором случае без DDL). Прямой24→26 запрещён: сначала отдельно
пройти утверждённый24→25. Новая миграция создаёт только metadata-таблицы, индексы и
functions/trigger; существующие sales/sale_items не сканируются и не переписываются.
SCHEMA_LOCK734190249, lock_timeout2s/statement_timeout30s сохраняются в явном job.

Ниже **шаблон команды для оператора**, а не универсальная замена updater.
`COMPOSE` — уже проверенный массив `docker compose -f ...` **со всеми реальными
файлами в прежнем порядке**, включая churn, Calltrack, mTLS и image overrides.
Он не определяется вымышленным сокращённым списком. Переменные должны быть загружены
без печати секретов; SALES_CANDIDATE_IMAGE — immutable подготовленный образ.

```bash
: "${SALES_CANDIDATE_IMAGE:?Set the reviewed prepared backend image}"
"${COMPOSE[@]}" -f deploy/migrate.import26.explicit.override.yml config --quiet
# Только после подготовки и проверки rollback и отдельного одобрения DDL:
"${COMPOSE[@]}" -f deploy/migrate.import26.explicit.override.yml \
  --profile schema-maintenance run --rm --no-deps schema-migrate
```

Job выключает analytics automation в своём окружении, не редактирует сохранённые
политики. Успех: `SCHEMA_MIGRATION_OK expected=20261109_26`. При сбое/потере соединения
сначала проверить **фактическую** alembic_version и read-only preflight, не делать
stamp, downgrade или слепой повтор переключения. PostgreSQL DDL транзакционен;
сбой postcheck не доказывает, что DDL откатился.

## Переключение готовых образов и проверки

1. Сохранить управляемый YAML/image override до переключения. Выбрать candidate
   immutable ID в существующем контролируемом механизме; проверить Compose quiet.
2. Проверить импорты и `python -B start_backend.py --check-only --expected-revision
   20261109_26` в candidate по штатному preflight, затем переключить **только** backend
   без пересоздания db и зависимостей. Ни DB volumes, ни init scripts не трогать.
3. Проверить `/api/health`, actual container image ID == effective Compose image ID,
   успешный schema preflight26. Несогласованность YAML/image ID — ошибка установки.
4. Переключить готовый frontend; проверить `/vr/sales/` и открытие защищённого импорта.
   Если frontend неуспешен при здоровом backend26 — восстановить frontend/YAML для
   frontend, **не откатывать исправный backend без основания**.
5. Проверить в UI: пустой справочник, контроль/автопроверка/email выключены. Не запускать
   реальную загрузку или email ради smoke. Не выполнять тяжёлый отчёт/scan production.

Schema preflight26 проверяет frozen columns/types/nullability, PK, UNIQUE, FK RESTRICT,
CHECK-ограничения, выключенные defaults и включённый rule guard. Frozen контракт
работает и при старом ORM-наборе в rollback image. Это проверено native PG16, но
конкретный production Docker image и server-only overrides здесь недоступны.

## Первоначальная настройка — без автоматической активации

1. В «Настройки → Импорт → Подразделения» получить предварительный список200 последних
   файлов. Сверить вручную с1С: код, точное имя/утверждённый `{date}`-шаблон и формат
   даты, даты открытия/закрытия. Примеры из тестов не считать действующими магазинами.
2. Внести правила с реальными датами продаж. Проверить отсутствие конфликтов. По
   возможности использовать проверяемый HTML-период; не выдумывать даты нулевых XLS.
3. Утвердить **дату начала контроля**, не всю историю, и смещение sales_day относительно
   FTP scheduler23:55. До этой даты пропуски не создаются. После появления истории
   её нельзя переносить, скрывая уже найденные проблемы.
4. Включить только общий контроль (`enabled`), оставить automatic/email OFF. Если
   требуется результат законченного дня, явно подтвердить его окончание с причиной;
   «Обновить проверку» не подтверждает источник и не запускает импорт.
5. Сверить счётчики с журналом успешных ImportBatch, посмотреть unavailable/error.
   Убедиться, что поздний штатный файл устраняет issue, а история не пропадает.
6. Настроить существующий SMTP в его административном разделе, получателей в новом
   блоке. SMTP test отправляет реальное письмо: только после отдельного разрешения
   администратора. Новая функция сама не выполняет тестовую отправку.
7. С владельцем1С утвердить и реализовать **достоверный completion marker** (см.
   контракт в основном документе). Пока такого признака нет — автоматический контроль
   и рассылка остаются OFF; не заменять marker фиксированной паузой.
8. После явного одобрения включить automatic, выполнить цикл без email, сверить дату
   и завершение всех retries. Лишь затем включить email и проверить один согласованный
   реальный цикл, отсутствие дублей и историю SMTP-результатов.

## Откат без удаления данных

- **Ошибка доставки/сборки вне VPS/конфигурации до DDL**: переключение не начинать;
  восстановить только затронутый YAML. Backend не пересоздавать без необходимости.
- **Миграция не состоялась, фактическая схема25**: вернуть исходные YAML и старый
  image/launcher25 штатной проверенной процедурой, затем healthcheck и image ID.
- **Фактическая схема26, candidate не запускается**: сохранить все новые таблицы и
  историю. Использовать заранее проверенный maintenance rollback с новым bridge
  launcher и старым immutable image. Не применять downgrade26→25/удаление таблиц.

```bash
: "${SALES_ROLLBACK_IMAGE:?Pin the tested old backend image}"
: "${SALES_ROLLBACK_LAUNCHER:?Absolute reviewed revision26 launcher file}"
"${COMPOSE[@]}" -f deploy/rollback.import26.checked.override.yml config --quiet
# Переключение выполняет только оператор по согласованной процедуре.
```

Override оставляет все исходные mounts/networks/overrides, добавляет только read-only
bridge launcher и command `--rollback --expected-revision 20261109_26`, image и
выключенные runtime analytics flags. `--rollback` запускает Uvicorn **без lifespan**:
это временный режим чтения/обслуживания, без FTP, сценариев, новых проверок и email.
Не выдавать его за полное восстановление фоновых функций. Перед отключением normal
candidate при возможности отключить новый контроль/email в UI. Новые таблицы при
этом сохраняются. В UI старого frontend новый блок отсутствует.

После rollback проверить health и image ID против итогового effective YAML. При
ошибке сохранять исходные YAML/bridge/image IDs/логи, не очищать резервные данные и
не объявлять восстановление успешным. Для возвращения фоновых задач нужен исправный
candidate26, обычный согласованный запуск и повторное административное решение об
активации. Frontend можно вернуть отдельно. Деструктивный downgrade миграции намеренно
запрещён; историю audit/issues/notices не удалять.

## Что должен решить администратор

- Утверждённые подразделения и точные источники, включая будущие открытия/закрытия.
- Реальные даты интервалов; утверждённая первая дата контроля; offset и timezone.
- Как1С подтверждает завершение всех выгрузок/повторов, имя и жизненный цикл marker.
- Принимается ли блокировка исправленных файлов вместо неявного добавления продаж;
  кто и по какой существующей процедуре разрешает исправляющий переимпорт.
- Получатели, SMTP и разрешение на реальную тестовую/первую рассылку.
- Общая admin-сессия или доверенный mTLS actor; индивидуальный пользователь пока
  технически не определяется общей парольной сессией.
- Окно установки, свободный диск/память, проверенные prepared image IDs и способ
  согласованного обслуживания внешних timers/locks.
- Адаптация live updater для26 и репетиция rollback конкретного старого образа.

Ресурсные риски: небольшой дополнительный потоковый hash I/O на каждый новый файл,
небольшие metadata-таблицы, дополнительные соединения advisory locks; ожидается один
FTP cycle/SMTP sender. История растёт с числом файлов/проблем, без хранения бинарников
и копии продаж. Политика архивации истории требует отдельного решения, не автопurge.
Отсутствие marker/неподтверждённый период честно блокируют полноту, а не маскируются.
