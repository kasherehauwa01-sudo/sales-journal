# Автоматическое сохранение фотографий каталога

LookupProduct принимает необязательный `image_url: StrictStr | None = None`.
Старый API без поля совместим; extra="forbid" сохранён. Новую возможность
VRCatalog нужно развернуть до заполнения: старый ответ не удаляет фото,
но и не добавит новые.

save_results сохраняет непустую безопасную ссылку для matched-товара.
Используется существующая нормализация catalog_item_image_url (публичный
корень каталога, а не /api). Принимаются только HTTP(S) с host, без
credentials, пробельных/управляющих символов, обратных слешей и неверного
порта. javascript/data/file/ftp отбрасываются. Пустая, отсутствующая,
некорректная ссылка не затирает старую; непустая новая заменяет старую.
Само изображение не скачивается, HTTP-проверка URL не выполняется.
URL хранится для браузера: доступность и публичность конкретного ресурса
гарантирует VRCatalog, а не DNS/сетевые запросы синхронизатора.

Сохранение характеристик и checkpoint атомарно. Существующие CLI и worker
увеличивают revision и инвалидируют кеш после успешного пакета; revision
в ключе отчёта также защищает другие процессы от старого кеша.
local_catalog и merge_periods уже возвращают image_url. Получение фото через
карточку и remember_detail_image не изменены. На клиенте нужно заново
сформировать отчёт после обновления: уже показанные строки сами не заменятся.

## Заполнение существующих товаров

Новый процесс и миграции не нужны. Существующий opt-in worker поддерживает
`refresh`: пакетная сверка известных CatalogLookup по индексированному PK,
без прохода всей истории продаж, с сохранёнными refresh_cursor/refresh_upper.
Перед refresh должен завершиться первоначальный discovery. Существующий
курсoр продаж/cycle не сбрасываются. Прерванный refresh продолжается по своему
курсору после явной команды; после перезапуска автозапуска нет. Advisory lock
исключает одновременную CLI/worker-синхронизацию, пауза завершает текущий пакет.
См. также docs/catalog_background_sync.md.

Refresh обновляет все характеристики, а не только фотографии. Уже заполненные
фото тоже могут быть повторно проверены: это свойство существующей сверки,
а не отдельный backfill. Статусы not_found/ambiguous не стирают последнюю
сохранённую фотографию, но отчёт не использует несовпоставленный товар.
Пропущенные ссылки не считаются ошибкой и могут остаться пустыми до следующего
ручного refresh после исправления источника. Повторный цикл идемпотентен по
данным; timestamps/revision и счётчики обновляются штатно.

## Команды оператору — подготовлены, не выполнялись

После согласованного обновления кода Sales Journal и VRCatalog проверить
готовность существующего worker. Его подключение/сборка — отдельное действие
оператора по docs/catalog_background_sync.md. Не менять настройки Docker,
БД или память; в этом PR нет изменений конфигурации. Не включать worker
автоматически при деплое. Если он выключен, start возвращает 503.
По умолчанию пакет 100, пауза 1 секунда; существующие конфигурируемые лимиты
и проверки памяти сохранены. В условиях дефицита RAM не повышать интенсивность.

Предпочтительно административный веб-интерфейс: статус → «Сверить известные
товары» → при необходимости «Приостановить» → продолжить тот же refresh.
Для API использовать защищённый cookie-файл текущей административной сессии
(chmod 600; не включать в git, не показывать содержимое). Ниже пути — шаблоны,
их задаёт оператор; credentials не вставлять в команды или журнал:

```bash
SALES_BASE='https://kvasmix.ru/vr/sales'
ADMIN_COOKIE_FILE='/secure/path/sales-admin.cookies'

# Только статус
curl --fail --silent --show-error --cookie "$ADMIN_COOKIE_FILE" \
  "$SALES_BASE/api/settings/catalog-sync/status"

# Явный запуск/продолжение известного refresh (только после согласования)
curl --fail --silent --show-error --cookie "$ADMIN_COOKIE_FILE" \
  --header 'Content-Type: application/json' --data '{"mode":"refresh"}' \
  "$SALES_BASE/api/settings/catalog-sync/start"

# Корректная пауза после текущего пакета
curl --fail --silent --show-error --cookie "$ADMIN_COOKIE_FILE" \
  --request POST "$SALES_BASE/api/settings/catalog-sync/pause"

# Статус CLI, не запускает синхронизацию
python -m app.catalog_sync status
```

Для продолжения повторить start с mode=refresh после состояния paused/error.
Не сбрасывать refresh_cursor/cursor вручную. Если refresh уже начат до
обновления API, завершение обработает только оставшуюся часть; после окончания
нужно явно запустить новый полный refresh, чтобы обновить ранее пройденные записи.
CLI run также повторно сверяет товары в новом завершённом цикле, но сканирует
историю продаж, поэтому для существующего каталога предпочтителен refresh.

Проверка через PostgreSQL read-only сессию (не выполнялась здесь):

```sql
SELECT count(*) AS products,
       count(*) FILTER (WHERE nullif(trim(image_url), '') IS NOT NULL) AS with_image,
       count(*) FILTER (WHERE nullif(trim(image_url), '') IS NULL) AS without_image
FROM catalog_products;
```

Это счётчики ссылок, а не проверка доступности изображений. Проверить несколько
обычных отчётных строк и штатную карточку без массового открытия/скачивания.
Откат — вернуть коммит приложения: схема и сохранённые ссылки остаются,
старый код продолжает их читать. Новый API с image_url несовместим со старым
строгим LookupProduct, поэтому при откате сначала приостановить синхронизацию
и согласовать совместимую версию ответа VRCatalog.

## Оценка нагрузки и проверки

100 идентификаторов в одном последовательном lookup-запросе, до 250 по
существующему контракту; на 77 350 идентификаторов — примерно 774 успешных
пакета. Реальное число зависит от количества lookup, дубликатов и invalid,
оно не равно числу catalog_products. Нижняя составляющая пауз — около 13 минут
при 1 секунде; это не прогноз общего времени, которое включает API, SQL,
повторы и ожидание памяти. Никаких 77 тысяч параллельных запросов или загрузки
всего каталога; память ограничена текущим пакетом и небольшими строками URL.
Существующие размеры ответов/таймауты/backoff/контроль RAM сохранены.

Тесты: новый/старый строгий контракт, пустые и небезопасные URL,
нормализация, сохранение старого фото, замена новой ссылкой, повторный цикл,
фото в local_catalog и merge_periods, revision и инвалидация, заполнение через
существующий refresh без сброса discovery. Существующие тесты карточки,
матчинга, фильтров и остановки/возобновления worker также выполняются.
Все данные синтетические, API подменён. Backfill и production не запускались.
