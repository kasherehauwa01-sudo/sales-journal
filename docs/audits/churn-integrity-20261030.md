# Аудит несовпадения SHA256 Calltrack (30.10.2026)

## Источники и границы

VPS, его PHP-код, `/usr/local/libexec/calltrack-churn-pilot.py`, unit-файлы,
manifest и базы НЕ читались. Приведённые владельцем серверные состояния — входные
сведения, не результаты нашей production-проверки. Оба указанных SHA256 найдены
в истории публичного репозитория `kasherehauwa01-sudo/Calltrack`:

| --- | --- | --- |
| Проверенная старая | `81cc42b03e0f9f9510b30e2ad09450f9e1dca543` | `f04e422ee2881f4cca6fccb2e8818f631b5eeae6f227c8cc01d7ab48dbe56bbc` |

Это подтверждает происхождение доступных GitHub-версий. Совпадение с текущими

запущенного Docker backend или рабочей папки Calltrack без Git.

## Фактический diff

Меняется только `updateManagerTask()`:

```diff
- if(in_array($task['status'],['DONE','CANCELLED'],true))throw new TaskConflict(...);
+ if($task['status']==='CANCELLED')throw new TaskConflict(...);
  $status=$input['status']??$task['status'];
+ if($task['status']==='DONE'&&$status!=='DONE')throw new TaskConflict(...);
```

Новая версия допускает редактирование результата выполненной задачи без смены
`DONE`. `CANCELLED` остаётся неизменяемым. Проверки видимости/прав, optimistic
version, запрет смены назначения/срока/приоритета менеджером сохраняются
(`api/manager_tasks_service.php`, строки 103–125). Нельзя автоматически открыть
завершённую задачу повторно. История изменений по-прежнему записывается.

`createManagerTask()`, `findAutomaticManagerTask()`, проверка producer assignment,
бюджеты, резервирование и открытые слоты между этими двумя версиями не меняются.
Следовательно, нет основания отключать hash guard: он корректно обнаружил реальные
изменения. Нет и основания обновлять весь manifest сразу после `git pull`.

В репозитории Calltrack `tests/manager_tasks_view_test.php`, строки 27–35,
содержит проверки редактирования DONE, устаревшей версии, запрета DONE→OPEN,
чужой задачи, прав supervisor, приоритета и освобождения слота. PHP/MariaDB
исполнение этих тестов этой работой не подтверждено; просмотр кода не заменяет
проверку на отдельно выделенном стенде.

## Контролируемое обновление manifest

`backend/scripts/prepare_churn_integrity_patch.py` подготавливает **отдельный
patch из локальных копий**, не применяет его. Он принимает только указанную
новую PHP-версию по SHA256 и ровно одну старую hash-запись этого PHP-файла,
сохраняет прочие данные, требует идентификатор проверяющего и создаёт новый
файл patch с mode 0600 без перезаписи входа. Неподдерживаемый реальный формат
manifest — блокировка, а не повод угадывать или переписать его структуру.

Поддерживаются явные вложенные maps `filename → sha256`. Другие схемы надо
сначала проверить по копии реального manifest. Не использовать инструмент
для новых неизвестных SHA256 или для автоматического утверждения следующего
обновления Calltrack. Все остальные контрольные суммы должны пройти штатную
проверку исходного пилота.

После аудита и отдельного разрешения администратора:
1. Сохранить защищённый backup действующего manifest и сверить SHA256 копии.
2. Проверить фактический PHP-файл, его права, работающую папку и указанное изменение.
3. Подготовить patch на локальной копии, просмотреть его и выполнить `patch --dry-run`.
4. Повторно проверить, что live manifest не изменился с момента снятия копии.
5. Применить только проверенный patch, сохранив owner/group/mode и backup.
6. Перезапустить только read-only диагностику. Реальное создание задач — отдельный
   этап после остальных блокировок; hash match сам по себе его не разрешает.

## Прочие независимые блокировки

- Алгоритм `/2` и утверждённая `/1`: требуется новая явно утверждённая ревизия,
  а не SQL replace версии. В репозитории CLI — `app.analytics_automation`,
  `manage_policy()`/`release_churn()` в `app/services/analytics_automation.py`.
- Главный lifetime бюджет: `analytics_task_budget` (`approved`, `max_tasks`,
  `used_tasks`), `api/analytics_budget_service.php`, строки 4–26.
- Отдельный дневной бюджет: policy + `analytics_daily_budget` + reservations,
  там же строки 30–65. В просмотренном Calltrack дневной максимум 5 и проверка
  соответствия ledger счётчику; это версия политики бюджета, не версия модели
  риска. Не заменять её `/1` на `/2` вслед за алгоритмом.
- Отдельный lifetime cap по исходному менеджеру: `analytics_manager_pilot_budget.php`,
  до 5 автоматических задач для менеджеров 3/6 по истории CREATED. Общего остатка
  недостаточно для вывода о доступности менеджеру. Мониторинг не снимает этот cap.
- Producer из Sales Journal main требует VERIFIED и проверенную историю; он не
  переводит PRELIMINARY_MATCH в VERIFIED. В Calltrack существуют отдельные signed
  preliminary-процедуры (`analytics_preliminary.php`, `analytics_verified_approval.php`).
  Наличие 39 preliminary не доказывает разрешение producer main; фактический
  серверный V3 bridge надо сверить отдельно, не переносить ему неподтверждённые
  возможности из другого коммита.
- `ANALYTICS_SIGNALS_ENABLED=False` описывает встроенный worker, не является
  самостоятельным доказательством остановки внешнего systemd-пилота.

Количество созданных задач/остатки бюджета/даты запусков из production не
подтверждены. Лог `total lifetime budget exhausted` согласуется с механизмом
lifetime cap, но для точных чисел нужны фактические read-only данные.

## Отдельная граница контракта V3

В просмотренном `Calltrack/api/analytics_verified_approval.php`, строки 9–17,
проверяются `upstream_manifest` и `binding_receipt` с независимыми подписями.
Стандартный `Sales Journal/app/services/analytics_automation.py`, строки 167–184,
формирует свой approved envelope и не добавляет эти два поля напрямую.
Следовательно, нельзя объявлять прямую совместимость main → текущий Calltrack
без проверки фактического server-only bridge. Он может выполнять необходимую
адаптацию; его содержимое недоступно. Мониторинг не придумывает адаптацию,
не ослабляет подписи и не переносит trust из root status JSON в release.
Это самостоятельный пункт обязательного стендового/серверного аудита до запуска.
