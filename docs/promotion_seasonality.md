# Автоматическая сезонность кандидатов в акцию

## Методика (версия 1)

Используются два полных календарных года перед текущим годом: в 2026 году — 2024 и 2025. Суммы количества агрегируются PostgreSQL; исходные продажи не копируются. Каждый год нормируется на собственный среднемесячный объём, поэтому общий рост между годами не создаёт сезонность. Индекс месяца — среднее двух нормированных индексов.

Минимум в каждом году: 120 единиц, 20 положительных строк продаж и 6 активных месяцев. Нужны наблюдения в январе первого и декабре второго года, а также присутствие всех 24 месяцев в общем источнике. Нулевые месяцы не доказывают отсутствие спроса: исторических остатков нет. Неполный/ошибочный импорт, отрицательные месячные суммы, ненадёжная идентичность или недостаточная история дают «Недостаточно данных».

Подтверждение: коэффициент вариации обоих лет >=0,35; корреляция месячных профилей >=0,75; доля одного месяца <=50%; индекс каждого сезонного месяца в обоих годах >=1,4. Сезон содержит 2–8 последовательных месяцев, включая переход декабрь–январь. Поддерживается несколько окон. Пики двух лет отличаются не больше чем на месяц и входят в подтверждённые окна. Единичный пик не подтверждается.

Уверенность — воспроизводимый эвристический балл, а не вероятность: `min(85, round(50*corr + 20 + 15*min(1,(strength-1)/1.5)))`; подтверждение требует >=70. Верхняя граница 85 отражает отсутствие истории доступности товара. Пороги консервативные, но ещё не откалиброваны на размеченной истории проекта.

Статус рассчитывается из сохранённого профиля относительно текущей даты: активное окно — «Сезон сейчас», до начала ближайшего окна <=45 дней — «Скоро сезон», иначе «Вне сезона». Неподтверждённый повторяемый профиль — «Сезонность не выявлена». Нет готового достоверного профиля — «Недостаточно данных». Неизвестный индекс отображается прочерком.

## Идентичность и ограничения

Ключ отчёта сохраняется: нормализованный код с приоритетом, затем артикул, затем имя. Ведущие нули сохраняются. SHA-256 вычисляется от ключа; хранится и исходный ключ для проверки. Изменение артикула при стабильном коде не разрывает историю. Разные коды не объединяются автоматически. Артикул без кода с разными нормализованными именами или неоднозначным сопоставлением локального каталога не получает сезонный вывод. Нельзя достоверно восстановить замену продукта под старым кодом без устойчивого идентификатора источника.

Профили общие для всех магазинов. Для сегментных выборок и исторического окончания отчёта количественное сравнение с общим ожидаемым спросом отключается. Исторические остатки не реконструируются. Начало и завершение известны с месячной точностью, прогноз не является гарантией спроса.

## Рекомендации и совместимость

Прежняя классификация, причины и стоп-факторы сохранены. Сезонный приоритет: 0 при недостаточном остатке/стоп-факторах; 40 для продвижения без обязательной скидки; 80 для сезонного кандидата с достаточным остатком и существующими основаниями; 95 при дополнительно слабых продажах относительно ожидаемых последних 30 дней; 100 для окончания сезона с избыточным остатком. Ожидаемый 30-дневный объём взвешивается по дням соответствующих месяцев. Исключение «Продажи растут без скидки» допускает только продвижение, не обязательную скидку.

При включённой сезонности сортировка: сезонный приоритет, число старых причин, стоимость остатка. `use_seasonality=false` возвращает прежнее ранжирование. Фильтр статуса независим от переключателя. Новые показатели находятся в добавочном блоке строки `seasonality`; корневой блок содержит актуальность расчёта. Excel сохраняет прежние 16 столбцов и добавляет 7. Изменения интерфейса применяются только по существующей кнопке формирования; никаких автоматических тяжёлых запросов.

## Хранение и выполнение

Миграция `20261012_17` после `20261010_16` создаёт только `seasonality_months`, `seasonality_profiles`, `seasonality_state`. Месячные количества Numeric(30,3); профили содержат индексы/ожидаемые количества и версию алгоритма. Исходные таблицы не изменяются. Состояние по умолчанию отключено.

Отдельная CLI использует существующий механизм сериализации тяжёлых операций, PostgreSQL advisory locks источника/лидера/каталога, проверки RAM и короткие SQL-таймауты. Импорт и удаление продаж уведомляют состояние в своей транзакции; пакет не выполняется одновременно с импортом или синхронизацией каталога. Зависшие queued/processing импорты нужно безопасно восстановить существующими средствами, а не автоматически объявлять завершёнными.

По умолчанию читается до 1000 позиций продаж по PK за пакет и рассчитывается до 100 профилей (до 2400 месячных записей), пауза 1 секунда. Все SQL-агрегаты ограничены диапазоном пакета. Сохранение агрегатов и курсора атомарно. После SIGTERM заканчивается текущий пакет; при принудительном завершении незавершённая транзакция откатывается. Следующий запуск продолжает checkpoint. Новая генерация публикуется только после полного расчёта. Старые поколения удаляются малыми пакетами; остаются текущая и предыдущая генерации.

Первый проход читает историю один раз ограниченными пакетами. Затем читаются новые ID и пересчитываются затронутые профили; ежедневная проверка обновляет актуальность. Исторический импорт с новыми ID учтён. Удаление продаж, смена пары лет/версии требуют нового поколения. Внешние UPDATE продаж в обход приложения должны сопровождаться явным rebuild. При недостоверном/устаревшем состоянии отчёт не использует старый профиль как достоверный.

## Безопасный запуск после проверки PR (команды не выполнялись на production)

1. Сделать проверенную резервную копию БД. Остановить длительные ручные операции; проверить RAM и состояние импортов. Согласовать окно миграции.
2. Обновить код, применить `alembic upgrade head` в backend. Не сбрасывать каталог или состояния существующей синхронизации.
3. Проверить `python -m app.seasonality status`: enabled=false. Первое ограниченное заполнение:

```bash
python -m app.seasonality run --max-batches 5 --scan-size 500 --profile-size 50 --pause 2
python -m app.seasonality status
python -m app.seasonality pause
```

Повторный `run` продолжает сохранённый курсор. После небольшой партии проверить RSS, доступную RAM, диск/WAL и длительность SQL; только затем продолжать. Верхний ID не является числом товаров, процент по ID не показывается. До публикации полного поколения сезонные показатели будут недостаточными, старые критерии отчёта работают.

После полного заполнения и проверки можно **явно** включить ежедневный режим:

```bash
python -m app.seasonality enable
python -m app.seasonality worker --scan-size 1000 --profile-size 100 --pause 1 --poll 60
```

Worker должен запускаться отдельным управляемым процессом **в том же backend-контейнере**, где действует общий файловый lock тяжёлых операций. FastAPI BackgroundTasks не используется, Docker/стартап приложения не изменены. Альтернатива — операторский ежедневный cron `python -m app.seasonality scheduled ...`; ограниченный запуск может не закончить цикл за сутки, тогда нужны дальнейшие ограниченные запуски. Не включать одновременно несколько планировщиков. `pause` отключает дальнейшую работу; `enable` возобновляет; `rebuild` только отмечает необходимость перестроения.

Три последовательные ошибки памяти/вычисления отключают автоматический режим. Занятые ресурсы и импорт откладывают работу без быстрого повторения. Если метрики памяти недоступны, пакет не запускается. Лимиты RAM, кеша, TTL и Nginx не повышены.

## Откат и риски

Сначала `pause`, остановить только управляемый сезонный worker, дождаться транзакции. Переключатель отчёта отключает сезонное ранжирование. Для отката к предыдущему приложению новые таблицы можно оставить: они независимы. Downgrade до `20261010_16` допустим только после остановки нового кода/worker и отдельного согласования; удаляет только сезонные таблицы, теряет их результаты, не исходные продажи.

До 24 месячных строк на товар на поколение, плюс профили; текущая и предыдущая генерации увеличивают диск/WAL, не RAM всей истории. Нужны несколько соединений для advisory locks: проверить существующий пул и max_connections. Защита приложения не исключает OOM от других контейнеров. Полная SQL-производительность на 4,6 млн строк и фактическая дисковая ёмкость пока не измерены на production. Проверки и синтетические замеры не являются доказательством полного устранения системного OOM.

## Проверки и воспроизводимость

Изолированные тесты проверяют статистику, переход года, рост, выброс, несколько сезонов, идентичность/дубли, остановку/отмену/повтор, блокировки PostgreSQL, инвалидацию импортом/удалением, старый порядок, фильтр и Excel. PostgreSQL 16 использован только в отдельном локальном контейнере с лимитом 256 МБ; миграция проверена upgrade/downgrade/upgrade.

Синтетические команды (не запускать на production):

```bash
PYTHONPATH=backend python backend/benchmarks/benchmark_seasonality.py --run --products 27016
PYTHONPATH=backend python backend/benchmarks/benchmark_promotion_memory.py --run --rows 27016 --variant after
```

Сохранённые результаты — `docs/benchmarks/seasonality_results.json`. Сравнение отчёта выполняется с одинаковым fixture и контрольной суммой прежних полей. Сезонный микробенчмарк использует готовые агрегаты и подставной bounded reader, поэтому не измеряет реальные SQL, сетевую задержку и JSON-декодирование драйвером.

Последний замер 27 016 строк: прежний отчёт 136,117 МиБ RSS, новый с недоступными профилями 136,258 МиБ (+0,141 МиБ); контрольные суммы прежних полей совпали. Запуски шли одновременно: 9,31 и 9,81 с нельзя использовать как строгую оценку изменения скорости. Готовые профили измерены отдельно: присоединение 1,49–1,84 с, пик RSS 77,74–77,76 МиБ всего микропроцесса, 109 чтений не более 250 ключей. Последовательный расчёт профилей: 4,18–4,98 с, RSS около 49,19 МиБ. Tracemalloc отдельно: 14 880 байт для потокового расчёта, 28 323 824 байт для чтения/аннотации с synthetic fixture. Реальное декодирование отдельных JSON драйвером и SQL не включены. Новые профили не вычисляются в запросе отчёта.
