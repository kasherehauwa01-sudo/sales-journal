Основа ветки — актуальный origin/main `6c2de638d47736262c50fde0f1c12b69e06ed765`.
Исходный код не содержит AGENTS.md. FirstVDS агентом не посещался; рабочая база,
дамп и данные клиентов не использовались. Схема29, launcher, миграции, updater,
Docker Compose и настройки интерактивных отчётов не меняются.

## Установлено и не установлено

По предоставленным оператором сведениям PostgreSQL прервал именно
`INSERT INTO category_season_facts ... SELECT` с `statement timeout`.
Общие REPORT_SETTINGS в `app/services/report_execution.py` ограничивают
**один SQL**60сек, work_mem4MB, hash_mem_multiplier1, parallel workers0,
lock_timeout2сек. Около2мин53сек от старта попытки не являются временем одного
SQL: до фактов выполняются отдельные запросы и обращения Clients VR.
Настоящий production-план и объём spill не получены. Только по тайм-ауту нельзя
установить, был ли неверный join-план, дорогая группировка, нехватка RAM/диска
или нормальное выполнение большого запроса, не уложившееся в60сек.

`prepare_pairs()` создаёт transaction-local TEMP/ON COMMIT DROP. Продажи до
первого дня текущего месяца дают DISTINCT **две** пары `coalesce(code,'')`,
`coalesce(article,'')`, а не одно выражение `coalesce(code,article)`.
Поток разбит по500строк, identity вычисляется существующим Python-алгоритмом,
характеристики берутся из локального каталога. Пары остаются в исходном SQL-виде,
включая ведущие нули; присоединяются через AND обоих равенств. В конце уже есть
`ANALYZE` TEMP-таблицы. Индекса/ограничения уникальности на ней нет.

`freeze_clients()` вставляет в постоянную `category_season_clients` DISTINCT
`lower(trim(coalesce(client,'')))`, назначает row_number по имени и фиксирует
менеджеров/типы покупателей. UNIQUE(snapshot_id,name) подходит для lookup этого
словаря. Записи новой генерации ещё не закоммичены, поэтому автоанализ их не
видит; существующая статистика может описывать предыдущие поколения. При
отсутствии статистики PostgreSQL использует общие оценки, не реальную совместную
кардинальность выражений/измерений. Это риск плана, а не доказанная причина
production-тайм-аута. ANALYZE всего постоянного словаря затрагивает и предыдущие
поколения; его нельзя считать бесплатным эквивалентом анализа одного TEMP-набора.

Обычные B-tree code/article не являются индексами выражений coalesce. Индекс
sale_items.sale_id и sales PK соответствуют соединению продаж. Миграция20
создаёт `ix_sales_rfm_normalized_client_date(lower(trim(client)),sale_date)`;
`lower(trim(coalesce(client,'')))` фактов **не является тем же выражением**.
Убирать coalesce ради индекса нельзя: это изменит обработку NULL-клиента.
Фактическое наличие/валидность индексов на FirstVDS проверяется метаданными.
При чтении всей истории seq/hash scan может быть правильнее index scan.
Новый постоянный индекс без измерений не предлагается: его построение на
миллионах строк требует места/WAL/обслуживания и отдельного анализа блокировок.

GROUP BY включает категорию, клиента, магазин, бренд, производителя, год/месяц.
Количество итоговых групп может приближаться к числу исходных строк; текстовые
ключи и ограничение4MB допускают spill сортировки/HashAggregate. work_mem —
лимит узла, не всего процесса/запроса. Для вывода нужны Plan Rows/Actual Rows,
loops, hash batches, sort method, temp blocks и Disk Usage, не только общий RSS.

## Что изменено

Только безопасная наблюдаемость и инструменты стенда:

- Времена этапов admission/settings/directory/pairs/clients/facts/coverage/
  options/publication/retention. Контекст изолирован между asyncio-задачами.
  Время этапа включает его подготовку, это не server-side duration одного SQL.
- Отказ пишет stage, валидированный SQLSTATE, имя класса и время; не exception
  string, SQL, значения, snapshot ID, фильтры или имена клиентов.
- Для ошибки БД error_code теперь, например, `facts:57014`. Cancelled по-прежнему
  `cancelled`, interrupted — `worker_interrupted`. CLI добавляет SQLSTATE.
- SQL вставки вынесен в общий `facts_statement()` для одинакового запроса в
  приложении и стенде; тест сравнивает его байт-в-байт с SQL установленного релиза.
  Имя TEMP строго валидируется. Расчёты/фильтры/NULL/публикация не меняются.
- Тайм-аут построителя **остаётся60сек**. Это не исправление производительности;
  установка диагностики сама по себе не является основанием повторить fill.

Locks WORKER/SOURCE/CATALOG, защита импорта, headroom, heavy-operation admission,
REPEATABLE READ и единый commit фактов/указателя сохранены. Ошибка до публикации
не заменяет предыдущий активный снимок. Первая неудача не включает расписание;
ручной повтор не блокируется уникальным week (у manual он NULL). Плановая
неудача по существующему правилу не крутится бесконечно в ту же неделю.

## Метаданные на FirstVDS — только оператором, по умолчанию без агрегации

После ревью/установки диагностического backend оператор может выполнить
**внутри согласованного контейнера**:

```bash
umask 077
python -m app.category_snapshot_diagnostics > /operator/private/snapshot-metadata.json
```

Внешнюю exec-команду определяет оператор по проверенной конфигурации. Не
печатать .env, весь inspect или SQL-логи. Модуль не вызывает rebuild/materialize,
не создаёт TEMP и не выполняет DISTINCT/GROUP BY/ANALYZE/EXPLAIN. Транзакция
READ ONLY, statement_timeout3сек, lock_timeout500ms. Он читает только настройки
из whitelist, pg_stat_user_tables, ограниченные index definitions/pg_stats
(без most_common_vals/histogram_bounds) и накопленные temp_files/temp_bytes.
Оценки n_live_tup/n_distinct — не точные подсчёты. Накопленные temp-счётчики
относятся ко всей БД после stats_reset, не к неудавшемуся INSERT. Настройки
в JSON относятся к диагностической сессии, не к предыдущей попытке построения.
Файлу дать закрытые права, проверить содержимое перед передачей.

**Точный план FirstVDS только из этих метаданных получить нельзя.** TEMP-пары
удалены при rollback; создание настоящих пар и нового клиентского словаря требует
тяжёлой подготовки. Не повторять её на FirstVDS ради EXPLAIN без отдельного
разрешения и не подменять план EXPLAIN на пустых TEMP-таблицах.

## Sales29Lab: одинаковые данные, планы и ограниченный сравнительный тест

Обновление лабораторного скрипта: [no_nested_loop и SAVEPOINT](category_snapshot_no_nested_loop_lab.md).
По умолчанию теперь baseline/no_nested_loop; старый эксперимент клиентов требует
явного `--comparison analyze_clients`. Результаты smoke ниже — исторический
опыт с ANALYZE clients, не результат нового варианта.

Нужен PostgreSQL16 в выделенной локальной БД `category_snapshot_lab`, без рабочего
дампа и production-подключений. URL с паролем задаётся локально через
LAB_DATABASE_URL (не публиковать). Скрипт отвергает не-localhost и другое имя БД.
Проверить DockerRootDir и диск PG data/temp: `docker info --format '{{.DockerRootDir}}'`
и `df -Pk` по **фактическим** путям; ещё свободную RAM/конкурирующие задачи.
Учитывать source heaps/indexes, два набора фактов, сортировки/хеши, WAL для
полноценной схемы. Temp_file_limit не ограничивает TEMP TABLE heaps и не заменяет
проверку диска. В среде Codex Docker storage0КиБ — нагрузочный тест не запускался.

```bash
PYTHONPATH=backend python -m benchmarks.benchmark_snapshot_facts \
  --confirm-synthetic-lab --sales 25000 --items 100000 \
  --products 10000 --clients 2000 --repetitions 2 \
  --output /operator/new-results/snapshot-facts-100k.json
```

Сначала маленькая проверка; затем при подтверждённых ресурсах масштабировать,
например, до ориентиров1,19млн продаж/4,6млн позиций из прежней диагностики.
Это ориентиры, не заново измеренные текущие объёмы FirstVDS. Число клиентов,
корреляции товаров/магазинов и ширину строк сверить с метаданными. Прогнать
несколько явно синтетических распределений, не выдавать их за реальные.

```bash
PYTHONPATH=backend python -m benchmarks.benchmark_snapshot_facts \
  --confirm-synthetic-lab --sales 1190000 --items 4600000 \
  --products 36706 --clients 20000 --repetitions 4 \
  --output /operator/new-results/snapshot-facts-4m6.json
```

20000клиентов здесь — synthetic assumption. Все объекты временные в pg_temp,
ввод генерируется PostgreSQL, не большим Python-списком. Обрабатывается точный
INSERT приложения, baseline и выбранный лабораторный вариант на одном наборе,
в одинаковых настройках. Клиентский TEMP-словарь пересоздаётся перед каждым
вариантом, чтобы статистика не перетекала в baseline; порядок чередуется.
Это исследовательский вариант, он НЕ включён в production-код. У него один
словарь, а у production — несколько поколений и FK-проверки фактов; исходные
строки/профиль уже и SQL-диск меньше14ГБ. Проверять реальную схему отдельно.

Для каждого варианта сначала сохраняется **EXPLAIN (FORMAT JSON, SETTINGS)**
без ANALYZE на уже заполненных таблицах и актуальной статистике источников/пар.
Затем только на стенде выполняется EXPLAIN (ANALYZE, BUFFERS, SETTINGS, FORMAT JSON).
В JSON — кардинальности, время, планы, totals и полное EXCEPT ALL всех измерений,
units/revenue/lines без загрузки результатов в Python. Изменение хотя бы одной
строки останавливает сравнение. Temp read/write blocks — объём I/O (block size
в отчёте), не peak файла; sort Disk/Space Used и Hash Disk Usage — по узлам.
Не суммировать включающие дочерние узлы счётчики как независимые файлы.

Для EXPLAIN без ANALYZE в полноценном лабораторном построителе использовать
**ту же открытую транзакцию** после prepare_pairs/freeze_clients; имена TEMP и
sid принадлежат этой транзакции, должны быть заполнены, статистика актуальна:

```python
plan = await db.scalar(
    text('EXPLAIN (FORMAT JSON, SETTINGS) ' + str(facts_statement(pairs))),
    dict(sid=sid, end=end),
)
```

Это не самостоятельная команда для production и не предложение вызвать
prepare_pairs/freeze_clients там. Сохранять только синтетические планы;
production-планы перед передачей проверять на литералы/чувствительные данные.

Лимиты стенда: report settings60сек/4MB/serial, локальный temp_file_limit1GB.
Если baseline прерывается, отдельная попытка получает status=failed/phase/SQLSTATE
и estimated plan; SAVEPOINT позволяет проверить второй вариант. Общий JSON
может быть partial/failed; незавершённые результаты не сравниваются. Только после оценки ресурсов
можно отдельным прогоном передать `--sql-timeout-seconds 300` (не более300).
Оба варианта получают одинаковое значение; это **только стенд**, не патч runtime.
Глобальные настройки PostgreSQL не меняются. Для temp_file_limit нужны права
SET этого параметра; при их отсутствии скрипт отказывает, не снимает ограничение.
При достижении лимита PostgreSQL отменяет SQL с53400, транзакция откатывается.
Runtime-предел не добавлен: значение/права/запас диска пока не обоснованы.

## Фактически проверено

Нагрузку FirstVDS воспроизвести не удалось. Выполнен только smoke SQL harness:
50продаж,200позиций,40пар,10клиентов,78итоговых групп. Оба варианта дали ровно
200строк-источников,200единиц и выручку203, точное EXCEPT ALL не нашло различий.
Последний сохранённый smoke: вызов EXPLAIN ANALYZE baseline3,740ms,
ANALYZE clients3,912ms (server Execution Time2,002/2,005ms). Один тёплый
запуск такого размера **не доказывает ускорения**; планы имеют одинаковую форму,
оба без temp spill. На join оценка1строка при фактических200; Aggregate оценка1
при фактических78. ANALYZE только клиентов эту ошибку оценки не устранил.
Поэтому он не перенесён в production и тайм-аут не увеличен.
Планы/последний smoke сохранены в `benchmarks/category_snapshot_facts_smoke.json`.

Итоговый профильный прогон: **28 passed, 1 benchmark deselected**,98,68сек
на изолированном PostgreSQL16.15. После добавления отдельного unit-сценария
неуспешного лабораторного JSON выполнены **7 unit tests passed**,1,07сек
(включают уже проверенные unit-тесты; эти числа не следует суммировать).
Black/compileall/git diff --check успешны. Полный backend-набор не запускался.

Профильные тесты проверяют неизменность SQL/итогов, права READ ONLY диагностики,
отсутствие бизнес-данных в сообщениях, реальный SQLSTATE57014, отмену, повтор
первого ручного заполнения и сохранение активного снимка при manual/scheduled
тайм-ауте. Дополнительный малый тест temp_file_limit0 проверяет SQLSTATE53400,
rollback и успешный последующий ручной запуск. Это не нагрузочное подтверждение.

## Следующая попытка FirstVDS после ревью

1. Ревью draft/диагностики; собрать образы вне VPS и установить согласованным
   updater уже-schema29, сверив IDs/Compose/mounts/backup и ресурсный запас.
2. Запустить только metadata-only модуль. Не повторять fill автоматически и
   не считать1,1–1,3ГБ RAM/5,5ГиБ прежнего замера текущей гарантией.
3. Завершить Sales29Lab-сравнение на близком объёме, изучить estimated/actual
   cardinality/spills и стоимость всех этапов, не только фактов. При необходимости
   подтвердить вариант temporary mappings/статистики/группировки и физические FK.
4. Только по результату подготовить минимальный performance-патч. Если запрос
   помещается в ресурсы, но требует больше60сек, обосновать отдельный конечный
   timeout snapshot и локальный temp-budget/права; лимиты отчётов не менять.
5. После отдельного ревью и установки этого **подтверждённого** исправления,
   проверки RAM/диска/temp/WAL/конкуренции и внешнего backup оператор осознанно
   запускает единственный `python -m app.category_seasonality fill --confirm`.
   Не запускать одновременно с updater/import, не снимать locks/headroom.
6. Проверить status=published, fact_rows и totals/выборку, active_id и next_due.
   Первая успешная публикация по существующему контракту включает ближайшую
   субботу19:00 МСК. При отказе — stage/SQLSTATE и actual state; не делать цикл
   повторов, не stamp/downgrade, не менять failed-строку/указатели вручную.

Откат этого диагностического релиза — предыдущий image schema29 штатным updater,
без изменения/удаления таблиц и снимков. Этот PR сам не устраняет60-секундный
тайм-аут на FirstVDS и не является разрешением новой попытки fill.
