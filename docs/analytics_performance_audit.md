# Аудит производительности аналитики

## Область аудита

| Раздел | Основные API | Источник расчёта | CatalogVR | Основной риск |
| --- | --- | --- | --- | --- |
| Общая аналитика | `/analytics/*` | `sales`, `sale_items` | HoReCa | повторные агрегации при смене фильтров |
| Товарная аналитика | `/reports/product-analytics/report`, `/details` | агрегация по SKU за два периода | `batch-info` | большой холодный расчёт |
| Продажи по товарам | `/reports/products/*` | документы и позиции | поиск и категории | несколько параллельных запросов страницы |
| Аналитика категорий | `/reports/category-analytics/*` | временная таблица SKU и агрегаты | `category-map` | повторное построение области выборки |
| Динамика продаж | `/reports/sales-dynamics/*` | агрегаты за два периода | нет | повторные `count distinct` |
| Аналитика магазинов | `/reports/store-analytics/*` | агрегаты по подразделению | категории | повторный расчёт детализации |
| RFM | `/reports/rfm/*` | агрегаты по клиентам | нет | полный экспорт и обогащение ClientsVR |

Запросы товарной аналитики уже используют единый endpoint и ограниченный
single-flight кеш. В рамках этого этапа механизм не дублируется. Клиент теперь
отменяет устаревшие HTTP-запросы, а справочники CatalogVR используют общий
ограниченный кеш с повторным использованием последнего успешного ответа при
кратковременной недоступности интеграции.

## Реализованный безопасный этап

* `batch-info` выполняется пакетами по 250 товаров с параллелизмом не более двух;
  частичная ошибка не удаляет результаты успешных пакетов.
* Кеш карточек CatalogVR ограничен 30 000 ключами и TTL 30 минут. Это исключает
  неограниченный рост памяти процесса.
* Справочники категорий, брендов и свойств имеют LRU-подобный лимит 128 ответов,
  свежий TTL 5 минут и stale-if-error до суток.
* React-хук запросов использует `AbortController`, поэтому быстрые изменения
  фильтров не оставляют заведомо устаревшие вычисления на backend.

## Локальный справочник: условие следующей фазы

Подтверждённый контракт Sales Journal содержит точечный `batch-info`, дерево,
бренды и поиск, но не содержит полного инкрементального потока с маркером версии
и списком удалений. Поэтому в этой фазе намеренно не создаётся таблица, которую
невозможно доказуемо синхронизировать. Для безопасного локального справочника
VRCatalog должен предоставить стабильный идентификатор, `updated_since`,
пагинацию, признак удаления и снимок/версию каталога. До появления этого
контракта отчёты продолжают использовать подтверждённые endpoints и последний
успешный ограниченный кеш; это не подменяет отсутствующие товары устаревшими
данными без явной диагностики.

## Индексы и развёртывание

Индекс `ix_sale_items_code_normalized` должен быть сверён с production через
`pg_indexes` перед отдельной миграцией. Создавать его повторно или строить
тяжёлые индексы внутри запуска приложения нельзя. Для таблиц объёмом в миллионы
строк новые индексы следует создавать отдельным оператором
`CREATE INDEX CONCURRENTLY`, после проверки `EXPLAIN (ANALYZE, BUFFERS)` на
production-копии и оценки свободного диска.

Рекомендуемый порядок выпуска: применить код без миграций, прогреть только
обычными пользовательскими запросами, контролировать RSS backend, число
таймаутов CatalogVR и длительности этапов в существующих логах. Откат — вернуть
предыдущий образ приложения; изменений данных и схемы в этом этапе нет.

Известные исходные измерения товарной аналитики: SQL основного периода 10,85 с,
SQL сравнения 61,40 с, CatalogVR 179,82 с, обработка 6,84 с. Production-замеры
после изменений не выполнялись: автоматическое развёртывание запрещено. Их
нужно снять после безопасного выпуска на одинаковом диапазоне и прогретом кеше.
